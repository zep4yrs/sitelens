01 / PROBLEM

为什么需要它

告警不是结论。

大多数扫描器把发现交给你，把判断留给你：这是误报吗？能复现吗？和代码里的哪一行有关？ 安全团队在排除，研发团队在猜。

01 / NOISE

扫到 200 条，复现 0 条

没有请求上下文、没有响应差异，只有一段 payload。研发无法判断真假，安全无法解释结论。

“先帮我看看这条是不是误报。”

02 / ENVIRONMENT

WAF 一拦，全变“疑似”

拦截页、软 404、超时和编码异常混进结果。扫描器把环境噪声当成漏洞，团队把时间花在排除上。

“这个 502 到底算不算？”

03 / SILOS

黑盒与白盒，各说各话

黑盒发现和代码审计结果对不上：一个说入口有洞，一个说 sink 有过滤，中间没有证据链。

“这两个报告说的是同一个问题吗？”

02 / METHOD

工作原理

三次确认，才写进结果。

SiteLens 不把“请求成功”当成“漏洞存在”。每一次判定，都要先建立基线、再做差分、最后留下证据。

STEP 01

预检与基线

输入 URL 后先发一次只读 GET，建立状态、响应体、时延基线；软 404、WAF 兜底页在这一步被识别。

1 次只读请求
基线：200 / 18.4 KB
STEP 02

差分与确认

同参数 benign / 攻击样本对比；状态码、响应体、回显位置多维差分，至少两次一致才进入验证。

2 / 3 一致
拦截 / 超时 / 编码异常剔除
STEP 03

证据与复现

生成可复制执行的请求证据与 curl 命令；黑盒发现可关联到白盒 AST 的 source / sink。

✓ 复现命令
证据链：source → sink
03 / CAPABILITIES

产品能力

从发现，到修复。

不是一堆检测器的集合，而是一条从发现、确认、证据到修复的闭环。高级能力默认关，边界写进配置。

05 / FIT

适用边界

它不是所有团队的解药。

如果一个工具声称什么都能做，通常意味着什么都做不好。下面是我们擅长和不擅长的。

适合

  • ✓需要给研发可复现证据的安全团队
  • ✓本地部署 / 数据可控，不接受 SaaS 托管
  • ✓想把扫描接进 Agent / CI / 报告流程
  • ✓接受“少而准”，愿意按验证口径复核

不适合

  • ×追求“一次扫出所有漏洞”的堆量场景
  • ×需要 SaaS 多租户托管 / 开箱即用集群
  • ×无人值守的自动攻击 / 写 shell
  • ×把扫描器当人工渗透的替代品
