> 版本：v1.1（2026-11-01 复评）
> 基线：v1.0（2026-10-30）
> 定位：正面竞争口径下的竞品对标、差距清单与追赶路线图  
> 适用：产品规划 / 研发排期 / 售前 POC / 融资与汇报  
> 数据口径：自身能力取自仓库 HEAD `f7c4e0a` 的代码/测试/文档（v1.1 复评）；竞品能力取自公开资料与一线反馈，**所有竞品分数均为内部初评假设，Phase 0 实测后校准**。
> 本文档取代此前“错位竞争”的建议：错位只适用于冷启动期；目标是对标，就按第一梯队的标准建设。

## 0. 结论摘要（一页纸）

**当前综合对标分 3.68 / 5，处于第二梯队上沿（第 4 名），距第一梯队门槛 3.8 还差 0.12。**

**三个判断：**

1. **验证与证据（4.75/5，第一）仍是立身之本，但只占 15% 权重**；v1.1 的总分提升主要来自覆盖（2.5→3.35）、企业化（1.5→3.45，SQLite 已实测、PG 驱动就绪）和部署/生态（4.5→4.9、2.0→2.7）。
2. **剩余差距已经换了性质**：覆盖/召回仍差第一梯队约 1.0–1.2 分且**没有实测数字**；企业化是“已接线、未规模验证”；生态/服务仍是短板。下一步涨分靠“实测 + 规模验证”，不是再堆功能。
3. **12 个月目标不变：综合分 ≥ 3.8（第一梯队边缘），验证专项保持第一，POC 胜率 ≥ 50%。** 现在只差 0.12，但这一步比前面从 2.85 到 3.68 更难——需要真实数据背书。

**最优先的 5 件事（v1.1 重排）：**

1. **真跑基准评测并回填验收报告**（OWASP Benchmark / WAVSEP / 靶场矩阵 / 授权真实站点），先把“召回/误报”从能力叙事变成数字；
2. **G09/G10 的默认策略与验收**：IDOR 会话材料入口、业务逻辑/上传的授权开关与发布说明（当前默认关 / dry-run）；
3. **企业化规模验证**：SQLite/PG、RBAC/租户、worker pool 在 2–3 家标杆环境压测，补 SSO/HA 设计；
4. **API spec 接进扫描计划** + 爬虫/认证继续拉满（覆盖最后 1 分）；
5. **生态落地**：MCP/辰极联调 demo、模板市场/SLA 从设计稿变成可交付。

**短期明确不做：** 主机漏扫自研、等保测评资质、0day 漏洞研究、全语言 SAST、自建云平台。这四项以集成/合作补齐，不占用主战线资源。

## 1. 对标范围与定义

### 1.1 竞品分层

| 层级 | 竞品 | 对标目的 |
|---|---|---|
| **核心对标（Web 应用扫描）** | AWVS(Acunetix)、Invicti、AppScan、xray、Goby、绿盟 WVS、安恒明鉴 | 同一张评分表、同一批靶场、同一批 POC，直接比 |
| **平台对标（主机/资产/合规）** | Nessus、Qualys VMDR、绿盟 RSAS、启明星辰天镜 | 客户常组合采购；短期做集成与结果导入，不做替代 |
| **开源基线** | nuclei + httpx + afrog、OWASP ZAP、Burp Suite Pro | 定义“免费能做到什么程度”，防止被白嫖型方案截胡 |

### 1.2 “硬碰硬”的定义

本文档不再讨论“要不要对标”，只讨论“怎么对标、对标谁、多少分、多久追上”。硬碰硬的口径是：

- **同一张评分表**：7 个一级维度、30 个二级指标、明确权重与评分锚点（见第 2、3 章）；
- **同一批靶场**：公开基准 + 教学靶场矩阵 + 授权真实站点盲测（见第 9 章）；
- **同一批客户 POC**：在客户现场用同一套评分卡打分，统计胜率；
- **赢的定义**：综合分进入第一梯队（≥ 3.8），3–5 个决胜项第一，POC 胜率 ≥ 50%。**不要求每个维度都第一。**

### 1.3 不参评项（诚实边界）

| 能力 | 现状 | 策略 |
|---|---|---|
| 主机/OS 补丁、配置基线、CIS/等保核查 | 不覆盖 | 短期集成 Nessus/OpenVAS/RSAS 结果导入；不自研 |
| 等保测评、密评、PCI 合规资质 | 无 | 报告模板做“可交付”，资质走合作 |
| 0day 研究与应急响应 | 无 | 短期依赖社区模板 + 情报合作；中期自建精选情报 |
| 全语言 SAST | 仅 py/js/php/java/go 污点分析 | 不扩语言，做深黑白盒关联 |

> 这几项不参评，不代表客户不买；代表我们不在这些战场投入主力资源，避免被拖死。

## 2. 评测模型

### 2.1 一级维度与权重

| 一级维度 | 权重 | 二级指标（示例） | 数据来源 |
|---|---:|---|---|
| 检测覆盖与准确性 | 25% | 漏洞类型覆盖、规则/模板规模、召回率、误报率、n-day 跟进 | 公开基准 + 靶场 + 盲测 |
| 攻击面发现 | 15% | 爬虫深度、SPA/JS、认证/多步、API/OpenAPI/GraphQL、资产发现 | 靶场 + 功能矩阵 |
| 验证与证据 | 15% | 二次确认、证据链、curl 复现、利用级验证、回归复测 | 靶场 + 人工复核 |
| 企业级能力 | 15% | 分布式、多租户、RBAC/SSO、资产台账、定时、报告/合规、集成 | 功能矩阵 |
| 性能与规模 | 10% | 吞吐、并发、大站点/万级资产、资源占用、稳定性 | 压测 |
| 部署与体验 | 10% | 安装/依赖、离线、跨平台、UI/易用性、数据更新 | 部署实测 |
| 生态与商业 | 10% | 情报/0day、插件/社区、服务/SLA、品牌/认证、价格/TCO | 公开资料 + 客户访谈 |

### 2.2 评分锚点（1–5）

| 分数 | 含义 |
|---:|---|
| 5 | 行业标杆，无明显短板，可作为该维度基准 |
| 4 | 第一梯队，能满足绝大多数客户 |
| 3 | 可用，但不是购买理由 |
| 2 | 明显短板，POC 会被问倒 |
| 1 | 缺失 |

### 2.3 评测方法（详见第 9 章）

- **公开基准**：OWASP Benchmark（约 2,700 个用例）、WAVSEP；
- **靶场矩阵**：DVWA、pikachu、sqli-labs、upload-labs、xsslabs、bWAPP、Juice Shop、WebGoat；
- **真实站点盲测**：20–50 个授权客户样本，人工标注 ground truth；
- **功能矩阵**：200+ 项 checklist，逐项打勾；
- **性能压测**：100 页 / 1,000 页 / 1,000 URL 批量 / 万级资产分布式；
- **成本模型**：3 年 TCO（授权 + 部署 + 人力 + 运维）；
- **反作弊**：版本冻结、靶场不硬编码、双人盲评、结果可复现、季度复评。

### 3.3 结论

## 4. 我们的现状：强项、平项、弱项

### 4.1 强项（必须放大）

| 能力 | 证据 | 对标价值 |
|---|---|---|
| 可离线复核的证据链 | 四件套（重放请求/响应快照/命中信号/curl）+ 二次确认 + `regression` 复测 | 唯一能“工具外自证”的扫描器；甲方交付/众测申诉/修复复测直接可用 |
| 误报治理机制化 | 软 404 基线、回显剔除、类内短路、WAF 拦截不判定（5.2） | 不靠规则调优，靠架构约束 |
| 零依赖部署 | 单二进制、无 DB/授权服务器/Agent、离线、无埋点 | 内网/涉密/单站点降维优势 |
| 单进程融合 | 指纹→情报→调度→DAST→模板→白盒→事实图 | 4.0 攻击链 + 黑白盒 evidence_link |
| 默认克制 | 主动能力默认关、5 rps、gov.cn 硬拒、SSRF/DNS rebinding/metadata 防护 | 可白天扫、合规友好 |
| 工程量化 | 29 万条 CVSS 对拍、benchmark、固定靶场零误报门禁、fuzz、govulncheck | 可信度本身是卖点 |
| Agent 可调用接口 | MCP stdio 13 工具 + 辰极 Lodestar 接入样例；scan/status/result/graph/export | 生态位：让 Agent 把扫描当工具，而不是替代品 |
| 输入体验 | URL 自动修正（补协议/去标点/hxxp 还原/全角/默认端口，留痕且不改目标） | 降低上手成本，同时守住“不改目标”的合规边界 |

### 4.2 平项（不拖后腿，但不构成购买理由）

- 模板规模与社区兼容（117,889 条可运行，但来源通过率仅 afrog 固化）；
- DAST 漏洞类覆盖（XSS/SQLi/重定向/穿越/盲注/SSRF/SSTI/命令注入/CRLF/NoSQL/XPath/LDAP/JNDI/XXE/上传受理面等）；
- 指纹库（13,727 条，但 5.0 对比暴露过 WordPress 漏识别）；
- ML 先验（只调序、不产生发现；收益案例小）；
- 性能（单页快，但默认限速导致大站点慢）。

### 4.3 弱项（对标失分项）

1. **覆盖仍有硬缺口**：召回无实测；API spec 未接扫描计划；G09/G10 默认关/dry-run；IDOR 需显式会话材料；
2. **企业化“已接线、未验证”**：SQLite/PG、RBAC/租户、worker pool 没有规模压测；无 SSO/HA/多节点；迁移 `--verify` 未交付；
3. **服务与生态**：无 SLA/0day/插件市场；中文单语、Windows-only 正式交付；
4. **质量证据**：靶场是教学靶场+自建夹具，无 OWASP Benchmark/WAVSEP/真实站点统计；benchmark 只有套件；
5. **产品化细节**：品牌更名暂缓；a11y 仍有 20 项允许例外（设置/历史/情报/反馈页标签待 5.3）；G09/G10 的配置与发布说明需补齐。

## 5. 差距清单（Gap List）

> 优先级：P0 = 入场券，不做就没资格上牌桌；P1 = 追平第一梯队；P2 = 企业化与反超。  
> 工作量：S ≤ 2 周，M ≤ 1 个月，L ≤ 1 个季度，XL > 1 个季度（按 5–7 人团队估算）。
> **v1.1 状态**：G01–G25 的落地状态与证据见 §13.2；本节保留 v1.0 的差距定义与原始优先级，便于追溯。

## 6. 三个必须赢的战场

### 战场 A：检测覆盖与召回（权重 40%，差距最大）

- **现状**：覆盖 2.5 / 发现 2.5；第一梯队 4.5 / 4.5。
- **目标（12 个月）**：覆盖 3.8 / 发现 3.8；OWASP Top10 全覆盖；CNVD 近 3 年高发 Web 漏洞 Top 50 覆盖 ≥ 90%。
- **关键动作**：G02/G03/G04/G05/G09/G10/G13/G14。
- **验收**：OWASP Benchmark TPR 进入商业扫描器中位以上；真实站点盲测召回 ≥ 80%、误报 ≤ 10%。
- **风险**：没有漏洞研究团队，靠模板生态追覆盖，质量参差；必须用“来源通过率+靶场命中率”双门禁。

### 战场 B：企业级交付（权重 15% + 生态 10%，差距最致命）

- **现状**：企业 1.5 / 生态 2.0；AppScan 5.0/4.5、Invicti 4.0/4.5。
- **目标（12 个月）**：企业 3.5 / 生态 3.0；功能矩阵 parity ≥ 80%。
- **关键动作**：G08/G11/G12/G16/G17/G18/G22。
- **验收**：能进 3 家大型企业 POC；采购 checklist 通过率 ≥ 80%；支持 10 节点分布式。
- **风险**：GPL-3.0、Windows-only、无 SLA 会被采购/法务卡；需要商业授权方案与服务包。

### 战场 C：性能与规模（权重 10%，决定大客户体验）

- **现状**：3.0；默认 5 rps/主机、单机、batch 50。
- **目标（12 个月）**：4.0；1,000 URL ≤ 30 min，万级资产分布式 ≤ 24h。
- **关键动作**：G07/G16；限速可配、分片、断点续扫、结果流式输出。
- **验收**：压测报告 + 客户现场实测；CPU/内存/带宽占用可解释。

### 决胜战场 D：验证与证据（权重 15%，必须保持第一并武器化）

- **现状**：4.5，第一。
- **目标**：5.0，并把“证据链”从功能变成**销售武器**：一键复现、离线报告、修复验证 SLA、CI 阻断。
- **关键动作**：G06/G23/G24 + 报告模板（甲方版/CI 版/管理层版）。
- **验收**：每个 POC 必演示“curl 复现 + regression 修复验证”；客户复核时间下降 ≥ 50%。

## 8. 竞品 Battle Card

### 8.1 vs AWVS（Acunetix）

- **对手画像**：国内乙方/甲方渗透最常用的商用 Web 漏扫，爬虫与规则成熟，SPA/HTML5 支持好，报告与品牌强。
- **它最强**：爬虫深度与覆盖、规则库、品牌与培训资源、存量客户习惯。
- **它最弱**：价格与授权、离线/内网部署、证据“工具外可复核”、攻击链/黑白盒关联。
- **我们怎么打**：同靶场同口径 PK；用“每条发现都能 curl 复现 + 离线报告 + TCO”打技术负责人；用“修复复测闭环”打运维。
- **必须补的课**：爬虫、认证、OWASP 覆盖、报告。**不补，POC 第一轮就被淘汰。**
- **演示脚本**：同一靶场跑同一批漏洞 → 双方各报 N 条 → 我们逐条 curl 复现并导出证据报告 → 展示 `regression` 修复验证。

### 8.2 vs Invicti

- **对手画像**：把“Proof-Based Scanning”做成品牌的公司，DAST+IAST+API，企业化成熟。**哲学上和我们最像，正面撞车。**
- **它最强**：验证深度、IAST、API 扫描、全球品牌与企业功能。
- **它最弱**：价格、本地化服务、离线部署、开源可审计、攻击链关联。
- **我们怎么打**：不比“谁有验证”，比“**证据能不能离开工具**”——curl 离线复核、GPL 开源可审计、零依赖部署；再用攻击链图打差异化。
- **必须补的课**：API/OpenAPI、企业化、报告；否则“验证”这张牌会被它用品牌压死。
- **演示脚本**：同一漏洞 → 它的证据在其控制台内 → 我们的证据是一条可在客户机器上重跑的 curl；再展示修复前后 regression 对比。

### 8.3 vs AppScan（HCL）

- **对手画像**：企业/金融/政府的老牌选择，报告、流程、多用户、合规最强。
- **它最强**：企业级功能、合规报告、品牌与渠道、服务。
- **它最弱**：价格、部署重、体验老、扫描速度。
- **我们怎么打**：短期不跟它在企业招标正面打；在**技术实测/POC/单点项目**用价格、部署、证据链取胜；中期补 RBAC/报告/合规再进企业。
- **必须补的课**：G12 报告合规、G16/G17 企业化。
- **演示脚本**：现场 10 分钟装完开扫 vs 对方服务端部署；用证据报告对比“可复核成本”。

### 8.4 vs xray（长亭）

- **对手画像**：国内“验证”心智占有者，社区版免费、POC 生态强、被动代理 + 主动扫描、反连平台。
- **它最强**：免费心智、POC 数量、被动代理、社区与实战口碑。
- **它最弱**：企业化、报告、资产管理、一体化体验、持续维护承诺（社区版与商业版有差异）。
- **我们怎么打**：打“**开箱即用的完整扫描器**”——爬虫/认证/报告/证据链/白盒一体化；打“企业级服务与持续维护”；打“攻击链与黑白盒关联”。
- **必须补的课**：POC 规模、被动代理模式、反连能力、CLI/性能。
- **演示脚本**：同一站点 → 我们全流程一条命令出报告；对比手工拼 POC 的工作量。

### 8.5 vs Goby

- **对手画像**：资产测绘 + 实战 POC，红队入口，免费版传播广。
- **它最强**：资产发现、端口/指纹、实战 POC、界面化。
- **它最弱**：自动化扫描、报告、企业功能、白盒、持续运营。
- **我们怎么打**：打“自动化 + 报告 + 企业级 + 白盒 + 攻击链”；红队场景认可它的资产能力，我们就补 G03/G14 资产发现。
- **必须补的课**：资产发现、端口指纹、POC 规模。
- **演示脚本**：同一资产范围 → 它做资产测绘 → 我们做“资产→验证→证据→攻击链”的完整闭环。

### 8.6 vs 绿盟 WVS / 安恒明鉴

- **对手画像**：国内老牌 Web 漏扫，合规报告、渠道、服务、招投标壁垒。
- **它最强**：合规交付、渠道、服务、品牌。
- **它最弱**：技术实测命中率/误报、价格、部署与体验。
- **我们怎么打**：技术实测 + 价格 + 部署；用“可复核证据”打其报告可信度；短期不碰纯合规招标。
- **必须补的课**：报告合规模板、服务包。
- **演示脚本**：同一靶场对比命中集合与证据质量；用第三方基准报告说话。

### 8.7 vs nuclei + httpx + afrog 组合

- **对手画像**：免费、灵活、模板生态强，但不是完整扫描器（无爬虫/认证/报告/资产管理）。
- **它最强**：免费、模板生态、速度、CLI 灵活。
- **它最弱**：一体化、爬虫/认证、证据链、报告、企业化、误报治理。
- **我们怎么打**：打“**一体化 + 可复核 + 报告**”；同时保持模板兼容，让它的生态成为我们的上游而不是对手。
- **必须补的课**：模板兼容度、CLI 体验、性能。
- **演示脚本**：同一目标 → nuclei 输出匹配结果 → 我们输出“发现+证据+复现+报告+修复验证”。

### 8.8 vs Nessus / RSAS（平台层）

- **对手画像**：主机/网络/合规扫描平台，客户常与 Web 漏扫组合采购。
- **它最强**：主机补丁、配置基线、合规、资产台账、品牌。
- **它最弱**：Web 应用深度、业务逻辑、证据链。
- **我们怎么打**：**不替代，做集成**——导入其结果、统一报告、用 Web 验证补它的短板；在“Web 应用验证”这一层做它的上游。
- **必须补的课**：G18 结果导入。
- **演示脚本**：Nessus 报“有漏洞的组件” → 我们验证“Web 层是否真的可利用” → 合并成一张攻击面报告。

## 9. 对标评测执行手册（POC / Benchmark Playbook）

### 9.1 输入

- 版本冻结：被测产品版本、配置、规则库版本全部记录；
- 靶场清单：见附录 B；
- 真实样本：20–50 个授权站点，人工标注 ground truth；
- 评分表：7 维度、30 指标、权重固定；
- 合规：仅授权目标；`gov.cn` 不参评；扫描流量与时间窗口报备。

### 9.2 步骤

1. **冻结**：版本、配置、字典、模板、网络环境；
2. **扫描**：统一模式（标准/深度/全量）与时间窗口；
3. **标注**：双人独立标注 ground truth，分歧仲裁；
4. **计分**：按 9.3 公式计算；
5. **复核**：抽取 20% 发现人工复核，确认误报；
6. **报告**：季度对标报告 + POC 一页纸；
7. **归档**：原始结果、命令、日志、截图，保证可复现。

### 9.3 计分公式

- Precision = TP / (TP + FP)
- Recall = TP / (TP + FN)
- F1 = 2 × Precision × Recall / (Precision + Recall)
- 覆盖率 = 已覆盖漏洞类型数 / 应覆盖类型数
- 综合对标分 = Σ（一级维度分 × 权重）
- POC 胜率 = 胜出场景数 / 总场景数（平局计 0.5）

### 9.4 反作弊与公正性

- 禁止针对靶场硬编码/特判；发现即判负；
- 每季度更换 30% 靶场与样本；
- 竞品使用官方最新稳定版与默认推荐配置；
- 评测人双盲，销售不参与计分；
- 结果对外发布需双方确认口径。

### C. 术语

- **TPR/Recall**：召回率，真实漏洞被检出的比例；
- **FPR**：误报率，非漏洞被误报的比例；
- **TCO**：总拥有成本（授权+部署+人力+运维）；
- **POC 胜率**：客户现场评测中胜出/平局的比例；
- **parity**：与第一梯队功能对等的程度。
