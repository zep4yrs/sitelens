## 0. 边界与禁令（全程有效）

- 5.0 核心是 Machine Learning（统计学习/排序/树模型起步）。**禁止**：
  LLM、RAG、Chat、Agent、Multi-Agent、Prompt Engineering、AI Chat UI。
- 本阶段**禁止**：在线自动攻击、自动化生产攻击、修改 3.0 扫描逻辑、
  修改 4.0 主线代码、把 ML 接入生产扫描流程、伪造训练数据/指标
  （Accuracy/Precision/Recall/F1/AUC 一律只来自真实运行）、改测试集凑指标、
  数据泄漏、用未来结果做特征。
- **负样本纪律（v2 新增）**：没有 execution 证据（该验证面确实执行过且未
  命中）不得生成 negative label；"没有 verified 记录"不等于负样本；
  不得为了完成 TODO 或提升指标人为构造正负样本。
- 提前实现 4.0 尚不存在的攻击链/CWE 关系/权限变化字段同样禁止——接口只做
  schema 定义（Phase 11）。
- 生成训练数据的主动扫描只在**自有靶场/自有资产**上做（农场
  `D:\fengqiao\ranges-lab`），exploit 开闸仅限靶场配置，不改默认值。
- 与现有结构冲突时以现有项目规范为准：数据目录 git 忽略策略、
  `data/state/` 只读、历史库格式冻结（审计报告 §16）。
- 语言：ML 流水线用 Python 3.13（本机既有），纯本地运行；
  依赖进 `ml/requirements.txt`（numpy/pandas/scikit-learn 起步，
  禁深度学习框架进第一阶段）。

## 0.5 第一阶段核心成果（v2 新增，最高优先级声明）

**第一阶段的核心成果不是"训练出高准确率模型"。**

第一阶段核心成果是一条**可重复、可追溯、无明显数据泄漏的 ML 数据生产线**：

```
真实历史数据 → Dataset → Feature → Label → Leakage Check → Split
            → Baseline → ML → Evaluation → Model Manifest
```

当前真实数据规模（审计报告 §7 实测，所有设计以此为前提）：
**119 scans / 10 hosts / 456 verified 行 / 1,135 intel 行**；exploit 判定
样本 0；可靠执行日志 0。在这个量级上，复杂模型和高指标既不可靠也不诚实。
模型选择固定为 Logistic Regression / Random Forest / Gradient Boosting
三族，基线固定为 Severity / CVSS / 现有 rule-based priority 三条，
全程不得为提高指标制造 synthetic 正负样本。

## 2. Dataset Schema（字段全部映射真实结构，无虚构字段）

粒度四层 + 一张静态特征表，主键与来源：

**D1 站点扫描表（scan 级，主键 scan_id）**
| 字段 | 类型 | 来源（真实结构） |
|---|---|---|
| sample_id | string | `{scan_id}` |
| target/host/ip | string | ScanRecord.URL/Host, Result.IP |
| scanned_at | datetime | ScanSummary.ScannedAt（存原始串+解析双份；**即该样本的 prediction_time**） |
| era | enum(py|go) | scan_id≤47 → py（审计报告 §9.4 实证） |
| options_known | json | ScanRecord.Options（原样，含缺失键标记） |
| duration_s/response_time_ms/status/error | num | Result 同名字段 |
| page_count | int | len(Result.Pages) |
| sec_score/sec_grade/sec_items[8] | num/enum/bool[] | Result.Security（security.go 8 头） |
| n_tech/n_vuln/n_verified | int | ScanSummary 计数 |
| data_origin | enum(history|archive|premigrate|matrix) | 文件来源指针 |

**D2 技术表（tech 级，主键 scan_id+tech_name）**：name、categories[]、
confidence、version、has_version、evidence_count、evidence_channel_types[]
（从 evidence 字符串前缀解析：header/meta/正则/src/内联JS/icon_hash/cookie/
关键词）→ 来源 engine.Tech（result.go:14-21）。

**D3 情报表（intel 级，主键 scan_id+cve+tech；同时是 T2 的 candidate
finding 来源之一）**：cve、tech、version、verdict、affected、severity_raw、
severity_norm（归一后）、cvss_score、cvss_sev、kev、n_templates_attached、
src、published_days（联 NVD.pub）、title/desc 文本统计 → 来源
intel.Finding（intel.go:66-86）。

**D4 验证表（verified 级，主键 scan_id+row_idx；同时是 T2 的 verification
target 来源）**：src、check、severity、url_path、param、has_payload、
confirmed、has_evidence_chain（request/replay/response/signals 五键齐）、
resp_status、resp_size、signals_count、impact（可空，显式 missing）、
evidence 文本统计 → 来源 verified map（审计报告 §8）。

**D4 v2 新增字段——observation/execution 状态**（修正点 1 的落地）：

| 字段 | 取值 | 语义 |
|---|---|---|
| execution_status | `executed` / `not_executed` / `unknown` | 该验证面在该次扫描中是否真正执行 |
| execution_basis | string | 判定依据说明（如 `options.checks 档位推断` / `无执行日志`） |

历史事实与推断规则（诚实口径）：
- verified 行本身 = executed ∧ 命中（命中才落库），天然 positive。
- 内置 check 的"被选中"可由落库的 `options.checks`（none/core/all）对
  37 条内置规则表推断，但**单次请求成败无记录**——推断不出可靠
  executed，一律 `unknown`。
- Nuclei 子集按 LRU 运行期选取（engine.go:681-719），DAST 探测集依赖
  爬取产物，执行集**不可复原** → `unknown`。
- 结论：**现有历史无法可靠产生任何 executed ∧ 未命中 的负样本**。
  Dataset 统计报告必须给出 execution_status 分布、unknown 占比、
  以及"可组合验证面（scans×适用 check/template）中 positive 456 /
  其余全部 unknown"的量级说明。**不得把 unknown 记为 negative。**

**D5 静态联接表（字典级，版本=字典文件 sha256）**：
CVE→(cvss 向量分解 AV/AC/PR/UI/S/C/I/A, kev, ransomware, pub, mod,
cpe products)；tech→(cats, conf, 有无 curated ranges)；template→
(path, tags, sev, proto, convertible, cves)；service_fp 行。
来源：data/nvd_cves.json.gz / intel_dump.json.gz / tpl_intel.json.gz /
affected_ranges.json / data/state/nuclei_index.json / data/go/technologies.json。

**隔离与追踪要求**：每行带 scan_id/host/scanned_at/data_origin；
split 元数据独立成文件；同一 host 任何情况下不得跨 split（见 §5 Phase 8
的 host/target 等价性规则）。

## 3. Feature 设计（全部标注 Prediction-Time 语义）

| 组 | 特征 | 语义 | 来源 |
|---|---|---|---|
| 资产/网络 | scheme、port、is_private_ip、host_tld、page_count、rt_ms、sec_* | P0 | D1 |
| 技术栈 | tech one-hot（115→频次截断）、cat 聚合 33 类、confidence 统计、version 覆盖率、共现 top 对 | P0 | D2 |
| 情报/CVE | cvss 分解 8 维、kev、ransomware、pub_days、src 类别、tpl_intel 覆盖、curated_range 有无、模板可用数 | P0（静态字典） | D3+D5 |
| 验证面 | check/template 元数据（lv、tags、sev、proto）、历史命中先验（**严格时间截断**，见下） | P0/P1 | D4+D5 |
| 证据强度 | confirmed、signals_count、resp_size、has_chain、evidence 长度/关键词 | P1 | D4 |
| 时序/时延 | timing 抽取数值（从 signals 正则提取 ms）、duration | P1 | D4/D1 |
| 认证态 | **缺**（结构化未落库）——特征位显式 missing | — | — |
| 攻击链/白盒 | **缺**——等待 4.0（接口见 Phase 11），Node/Edge/Path/Chain 特征已在接口草案预留 | — | — |

**历史先验特征时间截断（v2 硬规则，代码实现而非文档声明）**：

适用特征（穷举）：host 历史 verified 次数、host 历史漏洞（intel 行）次数、
CVE/check/template 历史命中次数、历史验证成功率、历史扫描结果聚合
（如该 host 上次扫描的安全评分）。

规则：对 prediction_time = T（样本自身的 scanned_at）的任何样本，
先验特征只允许聚合 `scanned_at < T` 的记录；**同一样本所属扫描自身、
以及 T 之后产生的全部记录禁入**。实现落点：
- `ml/features.py`：as-of 聚合器（按时间排序后前缀聚合，禁止全表 join）；
- `ml/leakage.py`：断言——随机抽取样本，重算其先验特征，逐一验证
  参与聚合的记录 scanned_at 均严格早于该样本 prediction_time；
  违例即 fail，评估不得开始。

禁止入特征：impact/impact_evidence、Extras["exploit"]、重放结果、
以及其他任何 F 语义（未来结果）字段——黑名单以断言形式在 Phase 5 实现。

## 4. Label 设计（可靠性逐条声明）

| ID | 标签 | 定义 | 可靠性 | 现状 |
|---|---|---|---|---|
| L1 | verified-hit | **三分**：executed ∧ 命中 = positive；executed ∧ 未命中 = negative；未执行/无法判定 = unknown（不训练、不进指标分母，仅统计） | positive 可靠；**negative 当前 0**（无执行日志，见 §2 D4） | positive 456 行可用 |
| L2 | template-verify-hit | (host, cve) 模板真命中 | 高 | 需受控靶场扫描生成（可选增强，不阻塞基础管线） |
| L3 | confirmed-verdict | 版本落受影响区间 | 高但近确定性规则（versioncmp）。**定位：sanity / pipeline validation 任务**——大量复用 version range / affected range / 情报匹配等既有规则，不是 5.0 核心智能能力，**不投入主要资源**，仅用于验证数据管线正确性 | 12 行 |
| L4 | regression-present | 回归重放仍在 | 高 | **可选数据增强**（Phase 5 选做），非基础 Dataset Pipeline 依赖；无 replay 数据时基础训练流程必须照常可运行 |
| L5 | exploit-proven | 利用级 proven/observed | 语义最优但**当前 0 样本，暂缓** | 靶场积累后启用 |
| L6 | 攻击链/权限/影响归因 | — | 不存在 | 等待 4.0 |

红线：Severity 不作为任何任务的 Label（只作基线/特征）；没有 execution
证据不得造 negative；不得为指标制造任何数据。

## 5. 任务定义（v2 收窄后的最终口径）

**T1 验证目标优先级（模板/check 执行结果预测）**
- 样本：目标 × 验证面（check/template）。
- 标签：L1 三分语义（§4）。**executed + verified/hit = positive；
  executed + not verified = negative；not executed = unknown，不得作为
  negative。**
- 数据现实：历史只记录命中（456 行 positive），无执行日志 → 可靠
  negative = 0，其余验证面组合全部 unknown。**T1 能否训练由 Phase 5
  数据 gate 按真实统计决定；不支持即延期，不得强行生成负样本。**

**T2 候选发现优先级排序（candidate-finding ranking，v2 收窄定义）**
- 输入：一次扫描产生的 candidate findings / verification targets
  （= D3 情报行 + D4 验证目标，附带该扫描的站点/技术栈/字典特征）。
- 输出：**ranking score + Top-K ranking**。
- 训练粒度：**scan × candidate finding**（备选 host × verification
  target）。不以 scan 或 host 整体作为训练粒度。
- 监督信号：候选是否进入 verified 的**观测正例**；未进入候选是
  unobserved 而非 negative，排序指标（P@K / nDCG@K）只定义在观测
  正例上，不把 unobserved 当负例计算。
- **对比义务**：T2 最终必须与 SiteLens 现行 severity 序 / CVSS 序 /
  rule-based priority 基线在同 split、同指标口径下对比（Phase 6/8）。

**T3** 站点级 sanity 回归（技术栈→verified 类别分布）：仅作管线自检。
**T4** 可利用性预测：暂缓（0 样本）。**T5** 验证策略推荐：暂缓。
**T6** 攻击链类：等待 4.0。

## 10. 模型接线方案（2026-09-29 开发规划，用户已阅）

5.0 模型线现状：三现役（cve-tech P@5 0.9083 / cwe-type acc 0.7709 /
sev-prior v3.1 分数 MAE 1.07）全部离线。本节定义接线架构、分层与落地顺序。
总原则：**模型只提供先验参考，不改变扫描行为与判定结果**；
一切预测带模型版本溯源（读 ml/model_registry.json）。

### 10.0 最终决策（2026-09-29 用户拍板）：L3 引擎内嵌

用户选择 L3：**模型推理直接嵌入 Go 引擎，取消 python 侧车**。
扫描完成即预测——引擎在扫描收尾时对含 CVE 的发现做推理富化，
结果作为 Result 增量字段随历史落库、经现有 API 暴露。

L3 架构（两阶段）：

**阶段 A：纯 Go 线性模型（cve-tech + cwe-type，零外部依赖）**

- 两模型同为 TF-IDF(120k) + 线性 OvR，纯 Go 原生移植：
  分词（sklearn 兼容：小写 + unicode 词字符 runs ≥2）、
  子线性 tf × idf、L2 归一、OvR 点积 + intercept
- 资产导出（ml/export_go_assets.py → data/go/ml_assets/）：
  vocab.txt（行号=id）/ idf.f32 / coef.f32（fp32 dense 起步：
  196×120k=94MB + 25×120k=12MB，惰性加载，后续可 int8/剪枝压缩）
- **parity 门**：500 条真实描述夹具上 Go 与 Python 预测对拍
  （top-1 一致 ≥99.5%、top-5 重叠均值 ≥4.5/5、cwe 一致 ≥99.5%），
  进 go test 常驻回归
- 零第三方依赖、零 DLL、零 python；引擎内存惰性 +94MB（仅预测开启时）

**阶段 B：sev-prior DistilBERT ONNX（二阶段增强）**

- torch → ONNX 导出（fp32 268MB / int8 ~90MB）+ Go WordPiece 分词
- 推理运行时：onnxruntime_go（cgo，onnxruntime DLL 随安装器分发）
- 显式披露：此阶段引入 cgo 与 DLL 分发——不装则分数输出降级"不可用"，
  AI 增强包可选补装

接入点与语义（不变）：模型只提供先验参考，不改变 check 选择与
severity 判定；预测与扫描判定物理分离；T1/T2 正例积累成熟后走同一
Result 字段位。

### 10.1 三层方案对比与决策（初稿，L2 细节保留为回退层参考）

| 层 | 形态 | 侵入度 | 用户可见 | 工作量 | 取舍 |
|---|---|---|---|---|---|
| L1 CLI | `sitelens-ml predict <record>` | 零 | 命令行用户 | ~0.5 天 | predict.py 已有大半 |
| L2 桌面面板（**推荐首做**） | Electron"AI 预测"面板 + python 推理侧车 | 仅壳层 | 全部 GUI 用户 | 2~4 天 | 侧车依赖打包是难点 |
| L3 引擎内嵌 | Go 内嵌 ONNX 推理 | 引擎 | 全部用户、无侧车 | 1~2 周 | 最彻底，与 4.0 内存预算冲突待评 |

决策：L1 立即补完；**L2 为 5.0 正式接线目标**；L3 列为 6.0 候选
（Go ONNX runtime 与引擎内存预算的冲突需先评估）。

### 10.2 L2 架构

```
扫描完成 → 壳读该次结果（现有 /api/history/{id}，只读）
        → POST 侧车 /predict（record JSON）
        → 面板渲染三卡片：
           cve-tech Top-5 产品 ｜ cwe-type 弱点类型 ｜ sev-prior 分数±区间
```

侧车（ml/serve.py，计划）：
- 进程：python HTTP 服务，127.0.0.1 随机高位端口，token 同引擎约定
- 生命周期：首次预测请求拉起，空闲 N 分钟自杀（对齐 4.0 资源治理哲学）
- 内存预算：≤400MB（BERT 走 ONNX int8 ~90MB + sklearn ~150MB + 推理峰值）
- 权限：只读传入记录，不碰 history.json，不发任何网络请求

推理运行时（关键决策）：
- 开发/实验：torch 直跑（现状，venv 已有 cu130）
- 产品分发：DistilBERT 导出 ONNX int8（270MB→~90MB），onnxruntime（~50MB）
  替代 torch（2.5GB）——安装器才带得动；sklearn 模型 joblib 原样
- AI 增强包：做成独立可选下载（基础安装器不含 python/模型，设置页一键
  补装）——对齐 4.0"默认轻量"哲学
- 门槛：ONNX 与 torch 预测对拍一致性 >99.9% 才可分发；不达标回退
  torch 侧车（安装器体积换工期）

### 10.7 深度融合落地（2026-09-29：前置先验 + 中段联动 + 后置富化）

用户拍板（"5.0 的扫描引擎要与模型深度融合"）后，ML 从"收尾贴标签"
升级为参与扫描调度。三个通道：

| 通道 | 时机 | 机制 | 落点 |
|------|------|------|------|
| 前置·产品先验 | 指纹识别后、check 执行前 | cve-tech 对「标题+检出技术+首页正文头部」预测 affected-product（Top-5，门槛 0.08、最多 3 个产品），产品映射到相关 check → 提权排序 + 核心档位扩展集增量纳入 | `internal/engine/mlprior.go` → `checks.RunChecksWithPrior` |
| 中段·家族联动 | check 运行中 | 一条命中后，同家族（wp/spring/bak/git/vcs/cms-login/dbadmin）未执行组统一提前（每家族至多一次） | `internal/checks/prior.go` 家族表 + runner 调度器 |
| 后置·预测富化 | 扫描收尾 | 发现 CVE 的产品 Top-5 / CWE 类型 / 严重度分数（既有 L3 阶段 A，不变） | `internal/engine/ml.go` mlEnrich |

**铁律（只增不删）**：先验只影响执行顺序与低档位增量纳入，绝不从执行
集剔除任何 check；命中判定条件、severity 展示来源不变；无先验
（prior=nil）时调度器退化为严格清单序，与 4.0 逐字节一致。ML 总闸
`ml.predict`（默认开）同时管辖三通道；任一环节失败静默跳过。

**调度器实现**（runner.go）：组（同路径聚类）得分 = 清单序基础分 +
boost×2×规模基数；命中联动同幅度加分；worker 每轮持锁领取当前最优组，
提权即时生效。执行证据（CheckRuns）如实记录调序后的执行序。

**A/B 实测**（本机 WordPress 仿站夹具 8099，core 档，workers=4）：

| 指标 | ML OFF（4.0 等价） | ML ON（5.0 融合） |
|------|------|------|
| 已验证发现 | 0 | **4**（wp-json medium / wp-readme / wp-xmlrpc / wp-login）|
| 执行 check | 10（核心集）| 15（核心 10 + 先验增量纳入 5）|
| 首个执行 | bak-dump（清单序）| wp-users（先验提权）|
| 可解释性 | 无 | extras.ml_prior：wordpress/wordpress **0.498** → 提权 5 项、增量纳入 5 项 |

cve-tech 纯凭站点文本（标题/正文里的 wordpress 词面）给出 0.498 置信
产品预测——指纹库没命中的产品，模型补上了探测方向。这回答了
"4.0 加不加 ML 数据都一样"：不加 ML，这 4 条发现在核心档位永远跑不到。

**回归护栏**：TestPriorNilKeepsListOrder（无先验=严格清单序）、
TestPriorBoostOrdering、TestFamilyBumpOnHit、TestFamilyBumpSingleShot、
TestMLProductChecks、TestIsExtended（internal/checks/prior_test.go）；
全仓 33 包 go test 全绿。

### 10.8 融合路线图：sev-prior（阶段 B）与 verify-rank（T1/T2）

**sev-prior v3.1——后置通道升级（已落地，2026-09-29）**：

- 阶段 B 工作流导出 ONNX（fp32 268MB + int8 69MB），三方对拍通过
  （torch↔fp32 MAE<0.02 / int8<0.05，logits 0-1 尺度）
- **引擎接入（internal/ml/sev_onnx.go，构建标签 `onnx`）**：纯 Go

  对齐——标点独立成词是关键分歧点）+ onnxruntime_go 会话；契约
  input_ids/attention_mask int64 [1,192] → logits ×10 = CVSS
- **对拍：Go vs Python fp32，n=120 全部逐位一致（MAE=0.00000）**

- 配置：`ml.sev_onnx`（默认关，桌面安装器形态开启）+ `ml.onnxrt_dll`
