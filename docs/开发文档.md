## 1. 项目定位

**SiteLens 站点透视**是一个结构完整的全类别验证型 Web 漏洞扫描器（当前版本
**2.0 验证器**），覆盖指纹识别、模板验证、DAST、认证扫描、网络层检测、源码审计
六大类攻击面。核心价值链：指纹识别 → 漏洞情报关联 → 模板验证引擎（117,883 条
可运行模板）→ 证据链报告（请求/响应/信号/复现命令）。

## 4. 设计原则

| 原则 | 落位 |
|---|---|
| 单二进制零依赖 | go:embed 前端 + 文件式存储 + 进程内出带 beacon（serve 与引擎同进程） |
| 全阈值可配 | .sitelens.yml 全量阈值注册表，零值/负值回退默认 |
| 宁少报不误报 | 漏斗准入（dsl Compile 静态校验，子集外整模板淘汰）+ 运行期类型错误一律不命中 + 命中二次确认 |

| 可再生数据 | 全量模板池不入仓库（体积考量）：update-* 子命令在线镜像 |

## 6. 功能模块

### 6.1 模板验证引擎（核心）

多来源模板漏斗：YAML → convertAny 转换准入（不可运行整条淘汰）→ 同名去重
→ 索引缓存（data/state/nuclei_index.json，schema v9，文件数失配自动重建）。

调度：MoE 三路 Select——① tag 硬匹配置顶（severity 升序）；② lastRun LRU
（从未运行的优先）+ 词面相关度（词频余弦）；③ 分批全覆盖保证（⌈全集/n⌉ 次
扫描后全池必跑一遍），lastRun 持久化于 data/state，重启不丢进度。

求值：dsl 安全子集求值器（Compile 准入 + Eval 求值，覆盖真实模板 96%+ 用法）；
多请求模板与 extractor 抽取变量贯通（Match.Extracts + respEnv vars），抽取版本
喂情报三级判定——possible → confirmed 的关键链路。

### 6.2 漏洞情报三级判定

confirmed：版本落在 OSV/GitHub Advisory 区间内。
possible：同名提示（无版本或无区间数据）。
excluded：版本不在区间，跳过不展示。

### 6.3 安全响应头评分

8 项加权（HSTS 20/CSP 20/XFO 10/XCTO 10/RP 10/PP 10/COOP 10/CORP 10），A+~F。

### 6.4 认证扫描

authn 登录流：配置凭证对登录端点表单提交，捕获会话 Cookie 全扫描复用
（爬虫/DAST/目录探测共用认证态）；凭证只从配置读取，不写日志、不落证据。

### 6.5 可选主动模块（默认关）

目录探测（软 404 基线+403 绕过表）/ 子域名枚举（DNS 并发）/
端口服务识别（nmap banner）/ FingerDir 路径指纹 / 子域接管探测（18 服务
CNAME+特征页双条件）/ 登录爆破（授权闸+宽容表单解析+基线判定）。

### 6.6 DAST

参数级无害注入（XSS/SQLi/重定向/遍历）+ 布尔差分盲注（真假 payload 双向
差分+双确认）+ SSRF 出带回调（进程内 beacon，/b/<token> 回连即确认）+
反序列化入口面探测（Java 序列化魔数 aced0005 响应特征，保守低危）。
全部探针命中带 curl 复现命令（证据链）。

### 6.7 被动检测

Cookie 属性 + CSRF token 只读检查（零额外请求）。

### 6.8 网络层

TLS 证书检查 / 邮件安全（SPF/DMARC/MX）/ 端口服务识别。

### 6.9 辅助能力

JS 攻击面（bundle API 端点枚举 + SourceMap 泄露检测）/ 无头浏览器渲染
（chromedp，SPA 链接可见，默认关）/ 验证码识别（本机 ddddocr HTTP sidecar，
未配置明确报错）/ 源码审计（16 规则静态匹配，RE2 兼容改写）。

## 12. 同类对比与改进路线

对比对象：Nuclei（引擎，MIT）与 Wapiti（同栈整车，GPL-2.0）。详细对比分析文档为内部资料，不在本仓库分发。

| 维度 | Nuclei | Wapiti | SiteLens |
|---|---|---|---|
| 形态 | 检测引擎（YAML DSL） | Python 扫描器（httpx 异步） | 扫描工作台 + 模板验证引擎（Go 单二进制） |
| 检测面 | 模板库 7000+，DSL/多请求/OOB | 29 主动模块（注入类深）+9 被动 | 模板池 117,883（MoE 调度 + tcp/dns/ssl 协议模板）+ 42 内置 check + DAST（注入/盲注/SSRF/反序列化）+ 利用级无害验证 + 验证回归 |
| 指纹/情报 | 无指纹情报层 | Wappalyzer 指纹，无情报层 | 2,853 指纹（372 自建 + 2,481 社区）+ 情报三级判定 + KEV |
| 吞吐 | 150 req/s | 异步并发 | 默认 400ms 间隔限速（合规取舍，全阈值可配） |
| 资产 | 无状态 | 无状态 | 文件式历史 + 双扫描 diff + JSON/CSV/HTML/MD 四格式导出 |

双向结论：检测面广度与注入深度对手占优（如实口径）；情报层、结果资产、源码审计、合规内建是我们独有。

改进路线：
- 已落地：命中二次确认 + 回显路径剔除（防自指误报，双向独有）；多源情报与来源追踪；CVSS 本地计分
- 已落地 P1：Cookie 属性/CSRF token 只读检测（passive 模块）；子域接管指纹表（takeover：18 服务 CNAME+特征页双条件判定，opt-in，候选封顶）
- 计划 P1 余项：同路径模板请求聚类提速
- 已落地 P2（部分）：DAST 表单字段探测（四类无害判定与 URL 参数同语义）
- 已落地 P2：模板 extractor 版本抽取喂三级判定（Match.Extract + refineVersion 回填技术版本，possible→confirmed 的关键链路）
- 不做：payload 注入类（与无害只读红线冲突）；GPL 代码零拷贝（只借鉴思路与数据格式）

### 13.1 设计决策记录

1. **存储**：PG → 文件式 JSON（data/state/history.json，tmp+rename 原子写）。
   单二进制可携带；行为契约（API 字段）不变。
2. **指纹匹配性能**：字面量门控（literalGate）先以子串存在性预筛，
   仅命中候选才执行正则——剖析驱动的 2.6x 优化（bench_test.go 固化）。
3. **Set-Cookie 保真**：Go http.Header 逐条分离，替代 Python 版
   合并头启发式切分（passive 模块因此删去全部切分判据）。
4. **规则形状容错**：technologies.json 历史导出中 194/370 条 html 通道为
   {dom,html} 对象形状，加载器双形状兼容（unmarshalRules）。
5. **取消语义**：JobManager 状态轮询在引擎阶段边界与 check 循环内生效，
   取消后局部结果不入库（对齐 Flask 版行为）。

### 13.2 遗留差距

已补齐（原差距 → 现状）：验证码 OCR → captcha 包接本机 ddddocr sidecar；
Nuclei 头匹配/dsl 匹配器 → internal/nuclei 漏斗 + internal/dsl 求值器全量
落地（多请求/抽取变量证据链已贯通，模板池 117,883 条）。

仍在：Python 污点分析（audit 为 16 规则静态匹配，非数据流污点）、
语义向量路由（语义检索以词频余弦近似）。3.0 起的范围见第 14 节。

## 14. 3.0 利用器开发实况（2026-09-12 立项并完成主体开发）

3.0 定位「利用器（Exploit Validation）」：从证明漏洞真实存在，到证明漏洞
能够影响。P1–P3 主体已落地（非 HTTP 协议检测 / 利用级无害验证 / 验证回归，
详见 docs/todo-3.0.md 勾选状态与 CHANGELOG v3.0.0），待发布流程（P6）。
开发范围定稿：

1. **利用级无害验证**：在 2.0 证据链（请求/响应/信号/复现命令）之上追加
   「影响证明」层——利用验证保持无害红线（不落盘、不提权、不持久化），
   以可观测副作用（回显/时延/出带）为影响证据。
2. **验证回归**：命中可重放、可回归断言；靶场回归门禁向利用级扩展。
3. **非 HTTP 协议检测**（2026-09-12 定入 3.0）：
   - 现状（立项时）：引擎与模板库均为 HTTP 专用——模板库仅镜像官方
     http/ 目录，network/dns/ssl/file 模板族不在池内；internal/httpx
     只会说 HTTP。【已落地：netx + 漏斗 v7 + 引擎路由，见 CHANGELOG】
   - 引擎侧：新增原始拨号层（TCP/UDP + TLS 握手 + DNS 查询），与 httpx
     并列；目标校验复用 internal/target 的协议白名单与保留地址闸。
   - 模板侧：漏斗准入 network/dns/ssl 模板族，索引与去重口径同现有来源。
   - DSL 侧：求值环境扩展原始响应（字节/行/多轮 send-receive），匹配
     语义与 HTTP 形态对齐。
   - 编排侧：按目标开放端口路由——Web 端口走现有流水线，服务端口走
     协议模板。

## 15. 5.2 变更（feat/sitelens-5.2.0，2026-10）

> 口径说明：本文 1–14 节描述 2.0/3.0 时期的 Go 主干（2026-09-12 核对）；
> 4.0（事实图/攻击链）、5.0（ML）见 `docs/开发文档-4.0.md` 与
> `docs/开发文档-5.0-ML预训练.md`。本节只记 5.2 的**结构性变化与口径订正**，
> 缺陷明细见 `docs/bug清单-5.1.0.md`，发版说明见 `docs/release-5.2.0/`。

### 15.1 引擎 / CLI 拆成两个二进制

- 新增 `cmd/sitelens-engine`：桌面交付线内置的**引擎二进制**，只提供
  `serve`（Web 控制台 + 扫描引擎）与 `update-seed`（随包只读种子 → 用户
  数据区的覆盖更新），**不含任何 CLI 子命令**；未知子命令直接报错退出，
  不静默当 serve 跑。
- `cmd/sitelens` 继续作为 CLI 控制台子系统（scan / serve / audit / correlate /
  graph-read / regression / migrate-pg / update-*），**不随桌面安装包发布**。
- 拆分动机：一个 exe 兼两职会带来桌面壳拉起时闪控制台窗口（BUG-032/033）
  与 CLI 能力白占安装包体积。引擎二进制**保持控制台子系统**（仍需写日志、
  `update-seed` 仍需输出结果），"不弹窗"由桌面壳以 CREATE_NO_WINDOW /
  HideWindow 实现，不靠改二进制子系统。
- 新增 `internal/seedcmd`（种子交付逻辑，两个入口共用）与
  `internal/seedrefresh`（种子比对/落盘/交付清单）。种子目录默认
  `<engine>/data`，按引擎版本收敛：版本变化才覆盖，同版本二次启动是 no-op，
  用户之后手动 `update-*` 的成果不会被覆盖。

### 15.2 诊断与反馈（无埋点）

- 新增 `internal/diag`：**本机**生成脱敏诊断包——版本 / 平台 / 运行时 /
  配置摘要 / 资产就位矩阵 / 降级能力 / 最近失败记录；路径只给文件名不给绝对
  路径，不含 token 与凭证。**不联网、不上报、不写用户目录**，无任何常驻采集。
- 新增 `internal/server/feedback.go` + `web/feedback.html`：
  `GET /api/diagnostics` 本地生成诊断包，`POST /api/feedback` 把用户确认过的
  文本转发到**用户自建**的收集端点（`[feedback] endpoint`，默认空 = 不提交，
  只能复制到 Issue）。本项目不提供也不运营任何收集服务端。
- 这是对《用户服务协议》「无埋点、无遥测、无崩溃上报」承诺的**兼容实现**：
  常驻埋点（FEAT-002）涉及协议修订，不在本版范围。

### 15.3 TUI 单一命令行入口与 `~/.sitelens` 用户区

- npm 线（`@fengqiao666/sitelens-cli`）是**唯一命令行入口**：交互式 TUI 与
  scan / audit / doctor / history / verified / serve / update / correlate /
  graph-read / regression / migrate-pg 全在这一个包里；Go CLI（cmd/sitelens）
  退回内部实现。引擎二进制随平台包自动分发，解析顺序：
  `SITELENS_ENGINE` 环境变量 → 平台包 `@fengqiao666/sitelens-<平台>-engine`
  → PATH 中的 `sitelens`。
- npm 线没有可写的安装目录，数据与状态统一落 `~/.sitelens/`：
  `config.yml`（TUI 管理的配置，幂等重写）、`data/`（资产）、
  `data/state/`（扫描历史，`store.data_dir`）、`.seed-manifest.json`
  （种子交付版本）。首次运行或引擎版本变化时自动把平台包内置种子交付到用户区。

### 15.4 模板漏斗：afrog rule 级 expression 接线（BUG-016）

- 背景：afrog 经典形态的判定**主要写在 rule 级 `expression`**（真实语料
  1,687/1,699 条有该字段，0 条写 `response:` 块）。旧 `afrogRule` 结构体缺
  `Expression` 字段，yaml.v3 静默丢弃未知字段 → 拼不出 matcher → 整个 afrog
  来源通过率为 0。
- 现状：`afrogRule` 补 `Expression`，由 `internal/afrogx` **转换期编译准入、
  运行期求值**；只有能诚实映射为"单请求 + 内容判定"的才转换（纯 `rN()` 布尔
  链，纯 && 或纯 || 两种形态）。
- 实测口径（packs/nuclei-templates.tar.gz 内 afrog 目录全量 1,699 个 yaml/yml）：
  **878 条（51.7%）可诚实求值并恢复运行，共转出 1,051 条 check**；其余 821 条
  按"宁少报不误报"拒收——AND 链某 rule 归一化失败 676（表达式编译失败/
  不可判定/无内容判定/路径占位符）、文档级表达式非纯 `rN()` 链 49、OR 全部分支
  拒收 48、多请求 AND 无法降为单请求 41、YAML 解析失败 4、文件过大 2、
  引用不存在的 rule 1。（数字来自本地全量语料实测，发版前复核。）
- 拒收口径（红线不变）：表达式编译失败 / 不可判定 → 整条拒收；含不可判定原子
  （`oobCheck` / 时延 / 随机标记等）→ 整条拒收；路径含 `{{}}` 占位符 → 该 rule
  拒收；多请求 AND 链无法诚实降为单请求 → 整条拒收；纯状态码不看内容 → 不转换。

### 15.5 模板漏斗：path 列表展开（BUG-022，上限 4）

- 旧实现 `normFromTpl` 只取 `path` 列表第 0 项（Wordfence 类 11 路径模板只探 1 条）；
  现按 `maxPathExpand = 4` 展开为多条 check（id 带 `~pN` 后缀，N 从 1 起；
  单路径保持原 id 不带后缀）。
- 上限 4 是预算兜底：真实语料多 path 模板约 10%，官库/40k 长尾最长 64 条，
  全量展开会按 64 倍消耗探测预算。长尾截断是**覆盖率损失（宁少报）**，
  不是误报来源；展开后各来源请求量约 +17%~36%。

### 15.6 索引缓存口径：`cacheSchema = 10`

`internal/nuclei/nuclei.go` 的 `cacheSchema` 演进：v5（raw 请求形态 + afrog 经典
形态接入）→ v6（Entry 增 CVEs）→ v7（协议模板准入 tcp/dns/ssl）→ v8（Entry 增
Source 来源类别）→ v9（afrog rule 级 expression 接线 + path 列表展开）→
**v10（模板索引热路径：缓存增目录 mtime 戳 `Dirs`）**。

- v9 起旧缓存里"仅 8 个来源可转换"的结论已失效，升级后必须整库重建。
- v10 起缓存文件额外保存「所有模板目录的相对路径 → mtime(unixnano)」：热路径
  只 stat 这些目录判断是否需要重建，不再 Walker 全池计数；同时包级保留一条
  「最近解码结果」memo（cachePath + 缓存文件 mtime/size 为键），避免每次扫描
  重复 JSON 解码。旧 v9 及更旧缓存整体失效 → 首次 Index 全量重建一次
  （满模板池约 8s），之后每次扫描走毫秒级热路径。
- 语义边界（与 v9 计数判定等价）：目录内文件增/删/改名都会更新父目录 mtime，
  所以「目录戳全等 ⇒ 文件计数不变」；**in-place 覆盖写**（同名文件内容更新）
  两边都检测不到，仍可删除 `data/state/nuclei_index.json` 强制重建。
- 注意 NTFS 目录 mtime 是毫秒级懒写：批量落盘后数毫秒内立即 Index 的极端时序
  可能把变更当成"未变"（宁少报方向，后续任一目录变动会补上）。

### 15.7 攻击链现状（4.0 建链口径订正）

> `docs/开发文档-4.0.md` 是 4.0 时期快照，其第 10 节 / 26.14 节保留了 P6 初版
> 的「同 host 归组 + 稳定 ID 相邻连边」表述。**现行实现以
> `internal/chain/chain.go` 为准**（快照文首已加注）：

- 建 `chain_node` 五类：`entry` / `exploit` / `recon` / `impact` / `priv`。
- `sequence` 边**只认真实因果**：入口点 → 落在该入口上的发现（经
  `VulnNode.EntryID`）；**没有 host 归组、也没有按稳定 ID 排序的相邻连边**。
  情报节点（`recon`，`intel:` 前缀）保留为上下文节点但**不参与串联**——
  P6 初版按「同 host 共享任意证据」连边时，实测 36 条噪声边（P8 修正，

- 其余三类边照旧：`exploit_impact`（vuln → impact，自带证据）、`evidence_link`
  （4.0 P4 黑白盒关联）、`priv_change`（P7 权限变化）。
- 铁律不变：`chain_edge.derived_from` 恒非空；无证据的候选边计入 `Skipped`
  而非强建；不依据 CVSS / CVE / 规则名或模型猜测造路径。
