## 先认识一下这个工具

SiteLens 扫一个网站，和普通扫描器最大的不同是：**每条发现都必须能被你自己亲手验证一遍。**

它会告诉你"在哪个地址、用什么方法、命中了什么信号"，并且给你一条 **curl 复现命令**——你复制粘贴到命令行，理论上就能重现它看到的东西。报告里还有完整的请求与响应片段。

这条"可复核"的承诺，是整个产品的立足点。这次体检发现的 3 个重要问题，有 2 个正好打在这个承诺上。

# 三个最需要你知道的

## ① 漏洞的"严重度分数"可能偏低，但绝不会偏高

### 这就好比什么

CVSS 分数（0~10 分）是业界通用的"危险程度温度计"：9 分以上是"严重"，7~8.9 是"高"，4~6.9 是"中"，3.9 以下是"低"。

我们在体检中发现，**SiteLens 抄错了这张温度计的刻度表**——抄错了两个数字，还漏了一步换算。

### 你会遇到什么

同一条漏洞，官方（NVD）标 9.9 分（严重），SiteLens 标 8.9 分（高危）。**看起来差了 0.1 分，但跨了一整档等级。**

我们用 29 万条真实漏洞数据做了逐条比对，结果是：

| | 占比 |
|---|---|
| 分数完全正确 | 58.58% |
| **分数偏低** | **41.42%** |
| **分数偏高** | **0.00%** ← 一条都没有 |

偏差最大能到 1.2 分以上，足够让一条漏洞从"中危"掉到"低危"，或者从"高危"掉到"中危"。

### 你要不要做什么

| 场景 | 建议 |
|---|---|
| 你用 SiteLens 的分数**排优先级** | 可以继续用，但**别把 9 分线当成"严重"的硬边界** |
| 你要**对外提交漏洞报告**（等保、众测、给甲方） | **必须用 NVD 官方分数核对一遍**，不要直接抄我们的 |
| 你看到某条漏洞落在 critical/high 的边界上（比如 8.9 分、6.9 分） | **人工复核**，这两档最容易被误判 |
| 你只看"有没有漏洞"，不看分数 | **完全不受影响** |

### 会不会造成误报

**不会。** 这个 bug 只会让分数变小。三处错误都是"少算"，没有一处是"多算"——所以它只会低估严重度，不会把不严重的说成严重。

### 我们怎么修

改 3 处代码（刻度表一个数字、补一步换算、换一个跟计算顺序有关的写法）。修完后我们用同样的 29 万条数据重算，**逐条与官方分数比对，100% 一致，零例外**。

## ② "一键复现"命令，可能被恶意网站做了手脚

### 这就好比什么

复现命令就像一张"快递单"，上面写着收件地址和包裹内容。你拿着这张单子去敲对方的门，对方一看单子，就知道你打算干什么了。

问题是：**这张单子上的字，是被扫描的网站提供的。**

如果对方是个恶意网站，它可以在自己的网页里塞进一些特殊字符，让单子上的内容"跑出地址栏"——你在终端里粘贴执行时，就顺手执行了对方塞的命令。

### 你会不会中招

需要**同时满足**三个条件：

1. 你扫描的是**恶意或不可信的网站**（不是你自己授权的靶场）
2. 命中的是**表单类**漏洞（登录框、搜索框、留言框这类）
3. 你**原样复制粘贴**了那条复现命令到终端执行

普通用户扫自己公司的系统、或跑公开靶场练手，**不会遇到**。

### 你要不要做什么

| 建议 | 说明 |
|---|---|
| 扫不可信目标时，**先用文本编辑器打开看一眼**那条命令 | 花三秒，能挡掉绝大部分风险 |
| 不要**盲目粘贴到有管理员权限的终端** | 复现命令本身是只读的 HTTP 请求，不需要高权限 |
| 如果命令里出现了你**没预料到的东西**（比如 `;`、`&&`、反引号），**立刻停手** | 这就是被做了手脚的信号 |

### 我们怎么修

项目里其实**早就写好了正确的转义函数**，只是表单这条路径没用上。改 3 行代码，让所有来自网站的内容都先转义再拼进命令。

**给使用者的额外提醒**：即使修好，转义后的命令也建议先看再执行——这是使用任何安全工具的通用好习惯。

## ③ 开了"允许扫内网"之后，可能顺带把云平台的临时密钥抓走

### 这就好比什么

有个开关叫 `allow_private`（允许扫描内网地址）。它是给"我有权扫描公司内网系统"这种场景准备的。

但我们发现，这个开关**顺带把另一道门也放开了**——云主机上一个特殊地址，专门存放"这台机器临时拿到的访问凭证"。

代码注释里明明写着"云厂商凭证地址永不放行"，但实际实现里，**按 IP 访问时这条保护失效了**（只有按域名访问才拦得住）。

### 你会不会中招

需要同时满足：

1. 你**开启了** `allow_private`（或设置页里的"允许内网"）
2. 你的扫描机**跑在云主机上**（阿里云、腾讯云、AWS、Azure 等）
3. 那台云主机**能访问到云元数据地址**（多数情况下能）

### 后果

云平台的**临时访问凭证**（IAM 角色、临时密钥）会被当成"网页内容"抓回来，**存进你的扫描历史和证据快照里**。

### 你要不要做什么

| 场景 | 建议 |
|---|---|
| 扫描机跑在云主机上 | **立刻检查**：历史报告 / 证据快照里有没有出现 `169.254.169.254` 开头的响应内容。有的话**当作已泄露处理**——去云平台把这台机器的临时凭证吊销重建 |
| 还没开始扫 | 在云主机上扫内网前，**先用网络策略把元数据地址拦掉**，或临时不开 `allow_private` |
| 扫描机是本地机器 / 物理机 | **不受影响** |
| 已经扫完、且不是云主机 | **不受影响** |

### 我们怎么修

把云元数据地址段挪进"永远禁止"的名单，让它不再受那个开关控制。改完会补一条测试：即使开了 `allow_private`，这个地址也必须被拒。

# 第四个：有一条方向是**相反**的，请特别留意

前面三个问题里，评分偏差是"偏保守"的方向——安全。但下面这条**相反**，它可能让你**多报**。

## 版本号比较可能把"不受影响"判成"受影响"

### 这就好比什么

工具要判断"你服务器上的 1.2.3.4 版本，是不是在漏洞影响的 1.2.3 及以下范围内"。

结果它只比较了版本号的前三段。**"1.2.3.4" 和 "1.2.3" 在它眼里是同一个东西**——于是明明比 1.2.3 新，它却说"你受影响"。

### 谁会中招

**带四段版本号的软件**。这类版本号很常见：

- Windows 补丁版本：`10.0.19041.1234`
- Java / Oracle 系：`4.17.3.0`
- 各种 `.0` 结尾的组件版本

### 你会遇到什么

在"漏洞情报关联"这一栏里，个别条目会被标成**「确认受影响」**，而实际上那个版本已经打了补丁。

**这是"误报"方向**——比评分偏低更需要警惕，因为它会让你去追一个其实不存在的问题。

### 你要不要做什么

| 建议 | 说明 |
|---|---|
| 看到「确认受影响」且版本号**带四段** | **人工复核**：查一下官方公告的受影响版本范围 |
| 看到「可能受影响」（possible） | 不受这条影响，正常对待即可 |
| 只需要"有哪些组件、什么版本" | 不受影响——版本号识别本身是准的，只是**和漏洞版本范围的比较**有问题 |

### 我们怎么修

改版本号比较逻辑，让它比较完整的四段（而不是固定三段）。会补上 `1.2.3.4`、`10.0.19041.1234`、`4.17.3.0` 这几个真实用例做回归。

## 其余 27 条是什么情况

剩下的缺陷不影响你看到的扫描结果，但影响工具的**稳定性**和**部署体验**。挑你可能碰到的说：

| 情况 | 你可能遇到的表现 | 状态 |
|---|---|---|
| **用桌面版** | **启动时弹一个黑色 cmd 窗口，退出时又闪一个** | 修复中 |
| **安装包太大** | 安装包约 744MB，其中 **84% 是模型资产**（4 个 ONNX 模型合计 643MB，fp32 与 int8 两套同时随包分发，实际只用得上其中一套） | 修复中 |
| **跑 Docker 镜像** | 容器里的情报库、CVE 库、模板库、ML 模型**都没有打包进去**，这些能力会静默失效（不报错，就是没结果）。另外容器以非 root 运行，历史记录可能写不进去 | 修复中 |
| **长时间连续扫描** | 遇到重定向的网站时，连接数会缓慢增长（每次跳转漏一个连接），跑久了可能报"连接过多" | 修复中 |
| **扫描过程中点"保存设置"** | 极少数情况下服务进程会崩（内部状态读写没加锁） | 修复中 |
| **命令行传参** | `sitelens scan <url> -config 配置文件` 这种写法，**配置文件会被悄悄忽略**（不报错）。正确写法是把 `-config` 放前面：`sitelens -config 配置文件 scan <url>` | 修复中 |
| **把结果发给同事** | 有一类漏洞的复现命令是 GET 格式，实际发的是 POST，**同事复现不出来** | 修复中 |
| **某些类型的注入检测** | 有两类注入（响应头注入、反序列化）实际没真正生效，单测是绿的但线上打不中 | 修复中 |
| **用社区模板库** | 其中一个来源（afrog，1699 条）**一条都没生效**——相当于白下载了 | 修复中 |
| **5.0 的 ML 严重度预测** | ONNX 模型通道打不开，一直在用兜底的旧算法 | 修复中 |

## 你可以自己做的两件事（约 10 分钟）

### 核对 ①：抽查几条漏洞的分数

1. 在 SiteLens 报告里挑 **3~5 条带 CVE 号的**漏洞
2. 去 [NVD 官网搜这个 CVE](https://nvd.nist.gov/vuln/search)，看官方分数和等级
3. 对照：如果官方分比你看到的高半档以上，记下来——这就是上面 ① 的情况

**最该抽查的是**：官方 9 分（严重）而你看到 8.x 分的，以及官方 7 分（高危）而你看到 6.x 分的。这两个边界最容易踩。

### 核对 ②：查有没有误抓云凭证

在报告或历史记录里搜 `169.254.169.254`：

- **搜不到** → 没问题
- **搜到了** → 说明你的扫描机在云上、且当时开了 `allow_private`。**去云平台把这台机器的临时凭证吊销重建**

## 我们做了什么，防止同类问题再次发生

这次能挖出 31 条，靠的不是运气，是几道具体的关卡：

1. **用 29 万条真实漏洞数据做全量对拍**——不是抽查，是**逐条比对**，所以"41% 偏高"这种问题不可能靠随机测试发现
2. **加了顺序无关性测试**——同一个漏洞，向量串换个写法顺序，分数必须一样（这次的 bug 正是栽在这里）
3. **补并发测试**——这次有多条"两个地方同时读写"的崩溃，CI 里的竞态检查抓不到，因为**测试没真并发跑**；我们补了并发用例
4. **加了"模板来源存活率"检查**——某个模板来源的通过率掉到 0 就告警（afrog 那 1699 条就是这样潜伏了很久才被发现的）
5. **加了"证据链可复现"检查**——每类发现的复现命令都要过 shell 语法检查
