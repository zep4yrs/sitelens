## 一、3.0 架构真实情况

### 1.1 技术栈与形态

- Go 1.26 单二进制，`go.mod` 直接依赖仅 3 个：chromedp（无头渲染）、pgx v5
  （仅 migrate-pg 历史迁移用）、yaml.v3。其余全部标准库 + vendor，零依赖纪律贯穿。
- Web 页面经 `web/embed.go` 编译进二进制；桌面形态是 Electron 壳（`desktop/`）
  spawn 引擎 exe，壳对引擎是黑盒进程边界。
- `cmd/sitelens` 10 个子命令：scan / serve / audit / regression / migrate-pg /
  update-nuclei / update-afrog / update-fp / update-osv / update-nvd /
  update-tplintel / update-ehole（`cmd/sitelens/main.go:29-126`）。

### 1.3 真实扫描数据流（沿 engine.go:117-582 逐段核实）

```
  └─ server /api/scan：store.Save 落 history.json                 server.go:558, 685

```

关键事实：**Engine 对外只返回 `*Result` 一个值**，中间产物（爬取的
ParamLinks/Forms、DAST 探测点 dastFormTargets）都是 Scan 内的局部变量，
扫描结束即丢弃，不进任何持久层（engine.go:206-207）。

### 1.4 依赖方向（import 实测）

```
server → engine, store, audit, intel, config, ...   （装配层，允许宽依赖）
store  → engine                                     （ScanRecord 内嵌 engine.Result）
engine → dast, checks, crawler, intel, modules, ... （不 import store、不 import audit）
audit  → config                                     （独立孤岛，引擎从不 import）
model(4.0 新增) → 无依赖叶子包（规划）
```

两个结构性事实对 4.0 重要：
1. **白盒（audit）与黑盒（engine）今天完全无连接**——没有共同数据模型，
   没有互相引用，甚至不在同一条命令流水线里。
2. **store 依赖 engine**（不是反向），engine 不知道存储的存在；
   4.0 图数据落盘应新增 `store → model` 边，而不是让 engine 学会写盘。

## 三、已有白盒能力（真实家底，全部）

### 3.1 internal/audit —— 508 行，SAST-lite

代码头注释自我定位明确（audit.go:1-10）："规则驱动 SAST-lite"、
"辅助人工复查的线索而非漏洞判决"、"移植自 python 分支，污点分析模块
暂未迁移"（后于 taint.go 以行级近似补了雏形）。

实际能力边界：

1. **16 条正则规则**（audit.go:33-75）：PY 10 条（eval/exec/pickle/
   os.system/SQL 拼接/MD5/硬编码密钥/debug 残留/tempfile/弱随机）、
   JS 3 条（eval/innerHTML/硬编码密钥）、PHP 2 条（命令执行/动态包含）、
   通用 1 条（内网 IP）。逐行匹配，无跨行、无上下文。
2. **TAINT-lite 行级污点近似**（taint.go，仅 .py）：
   - source：input() / request.args|form|values|cookies|data|json|files|headers / sys.argv
   - sink：eval/exec/os.system/os.popen/pickle.loads/yaml.load/subprocess.*
   - 规则：变量被赋值为污点表达式后出现在后续行 sink 参数中即报。
   - 头注释明确声明局限（taint.go:1-13）：**无 AST、无函数作用域、
     非流敏感**；不用完整解析器的理由是"无维护良好的纯 Go Python 解析器，
     守住零依赖原则"。
3. **输出结构**（audit.go:121-145）：Report{Findings, Files, Lines,
   BySeverity}；Finding{Rule, Severity, Title, File, Line, Snippet,
   Match, Advice}——无 ID、无 CWE、无函数名、无数据流步骤、无持久化。
4. **与扫描完全解耦**：CLI `audit <dir>` 打印 JSON 即结束（main.go:68-82）；
   API `POST /api/audit`（收 .zip/.py/.js/.php 上传到临时目录）与
   `GET /api/audit/demo`（运行时拼装教学靶样本）都是**算完即返，不落盘**
   （server.go:1065-1073, 1115-1125）。

### 3.2 白盒结论

- AST：没有。source/sink：仅 Python 行级近似。data flow：没有（行级
  赋值-使用近似不算数据流图）。taint：同上。CWE：**全仓 Go 代码
  `grep -rn "CWE|cwe" 零命中**。function/call relationship：没有。
  evidence persistence：白盒零持久化。
- 用户要求"不要假设这些能力已经存在"——审计结论：它们确实基本不存在，
  4.0 白盒线（P3-P5）是从 TAINT-lite 雏形向真实 AST/数据流的重建，
  不是升级改造既有重型系统。

## 四、Evidence / Verification / Store 当前结构（字段级）

### 4.1 "Evidence" 一词在本仓有两个互不相干的含义

1. `sitelens.Evidence`（evidence.go:12-23）：**指纹信号包**——URL/Status/
   Headers/Body/Title/ScriptSrcs/Metas/CookieNames/FaviconHash，供 Matcher
   消费，与漏洞证据无关。4.0 建模时必须换名或明确限定，避免歧义。
2. **发现级证据**：散落在各 Finding 结构的字段里，没有独立实体：
   - `dast.Finding`（dast.go:407-425）：Evidence 文本 + Payload（探针值）+
     Replay（curl 命令）+ Request（重放报文）+ Response（RespSnap：Status/
     Size/Snippet）+ Signals（通道信号明细）+ Hypothesis/Impact 扩展位。
   - `checks.Hit`（runner.go:27-42）：同构证据链（Request/Response/
     Signals/Replay/Confirmed/Hypothesis/Impact）。
   - exploit：impact/impact_evidence 回填进 verified map（exploit.go:60-62）。
   这套证据链是 3.0 的真实资产，4.0 Evidence 实体应从这两处提升，
   不是从零发明。

### 4.2 Verification 当前结构

- 验证语义分级已存在且诚实：checks（响应特征 + Confirmed 二次确认位）、
  DAST（探针+回显判定）、exploit（none/observed/proven，exploit.go:27-33）、
  replay（present/gone/unsupported，unsupported 不进回归分母）。
- intel 侧 Verdict：confirmed | possible（版本区间判定）。
- 但全部验证结论都汇入 **`Result.Verified []map[string]any`**
  （result.go:45，注释自认"异构条目统一 map 形态"）：键位靠约定
  （check/title/severity/url/evidence/advice/src/param/payload/replay/
  request/response/signals/confirmed/type/impact/impact_evidence），
  **无稳定 ID、无类型、无 schema**。这是 4.0 数据模型最大的债。

### 4.3 intel.Finding（情报结论，result.go:44 引用）

`{ID, Tech, Version, Src, Name, Title, Product, CVE, Type, Severity,
SeverityZh, CVSSScore, CVSSSev, Ref, Desc, Verdict, Affected, KEV,
Templates}`（intel.go:66-89）。有 CVE 无 CWE；`NVDEntry` 投影
（nvd.go:28-39）只保留 cve/pub/mod/sev/score/vector/descr/prods，
**原始 NVD 的 weakness(CWE) 字段在投影时被丢弃**——补 CWE 需要改投影
+ 重新跑 update-nvd，不是简单加个字段。

### 4.4 Store 当前结构

- 文件式：`data/state/history.json` 全量载入内存 + 写时 tmp+rename 落盘
  （store.go:1-8, 294-303）。损坏隔离为 .corrupt 从空库继续（74-79）。
- `ScanRecord = ScanSummary + Options map + *engine.Result`（40-44）。
- **无 schema 版本字段**（history struct 只有 NextID/Scans，47-50）。
- 超上限裁最旧 → 归档 `history.archive.jsonl`（JSON Lines 可回灌，110-132）；
  ClearAll 刻意不归档（隐私语义，199-212）。
- Job/JobEvent 纯内存不跨重启（317-421）。
- 历史数据现状：data/state 已 50MB（含 nuclei_index/nuclei_schedule/kev_extra）。

### 4.5 API 面（28 条路由，server.go:198-227）

scan/job/batch/history(4)/export/diff/vuln-search/verified/replay/netsec/
loginbrute/captcha/audit(2)/settings(2)/osv-sync(2)/stats/version/categories/
admin-reload + dev/spa-target + beacon 出带回连 `/b/{token}`。
扫描档位 7 预设在 `levelPresets`（server.go:460-468），
quick/standard/assets/stealth/full/apocalypse 等经 scanOptions 平铺映射。

## 五、4.0 目标模型 vs 现状：差距清单

用户目标实体 → 现状判定：

| 目标实体 | 现状 | 差距定性 |
|---|---|---|
| entry_point | Pages/ParamLinks/Forms 瞬时局部变量，扫完即丢 | **缺失**：需在 Scan 内收集成实体 |
| vuln_node（统一漏洞节点） | Verified 是无类型 map，黑盒白盒两种 Finding 结构不相干 | **缺失**：类型化 + 统一 ID |
| evidence（本体） | 字段级证据链已有（dast/checks），但非独立实体不可寻址 | **重构提升**：从字段变实体 |
| evidence_link（黑白盒关联） | 完全不存在（两岛无桥） | **缺失** |
| source/sink/dataflow | TAINT-lite 行级近似，仅 .py，无函数作用域 | **重建**：AST 级 |
| cwe_rel | 全仓零 CWE，NVD 投影丢字段 | **缺失** |
| chain_node/chain_edge | 不存在 | **缺失**（第一版只允许证据驱动建边） |
| priv_change | 零散原料：403 bypass 字段（modules.go:31）、loginbrute 命中、exploit proven，均无实体化 | **缺失** |
| impact | exploit 的 impact 字符串 + intel CVSS/KEV 先验，无实体 | **提升实体化** |
| schema 版本化 | store 无版本，导出无版本 | **缺失** |
| 稳定 ID | 除 intel Entry 自增 ID 外全无 | **缺失** |
| 5.0 ML 可读导出 | 无（history.json 是单体快照非记录流） | **缺失** |

结论：4.0 的核心工作是**新建统一数据模型层 + 一条黑白盒关联分析线**，
黑盒检测层基本原样复用，白盒层是重建而非改造。

## 七、多语言必要性裁定

**Go 主干不动摇**。4.0 全部编排/存储/API/关联/链建模在 Go 内完成，
理由：现有 26 包黑盒资产、零依赖单二进制纪律、桌面安装器/CI/AV 规避
（-ldflags "-s -w"）都绑定了这个形态。

**AST 解析器是唯一可能引入第二语言的点**，候选与裁定：

- 方案 A（推荐先试）：tree-sitter 官方 Go 绑定（CGO）。语法全
  （py/js/php/java/go），进程内无 IPC。代价：Windows 本机构建需要
  gcc 工具链、CI 产物特性变化需重验 AV 白名单、go.sum/vendor 面变大。
- 方案 B（A 证伪后备）：Rust 分析器 sidecar（独立 exe + JSONL 文件
  协议）。解析生态最好，但破坏单二进制、安装器双 exe、协议要版本化。
- 方案 C（否决）：纯 Go 解析器——Python 侧无维护良好的实现
  （audit.go 头注释已实证过这个判断），不可行。

裁定：**P3 第一步做方案 A 构建 spike（本机 + CI 各一次）；CGO 成本
被证伪才引入 Rust，且分析器输出统一走 graph JSONL schema——语言
切换被 schema 边界隔离，不波及其他层**。Python 仅属 5.0 ML，只读
graph JSONL，不进 4.0 执行链（现状已满足：python 分支独立文件夹）。

## 八、架构问题与最小改造方案（不推倒重写）

1. `Verified []map[string]any` 无类型无 ID —— 不改 3.0 输出键位，
   P2 引入 typed 结构与 map **双写**（适配器层），前端无感；
   graph 输出走新字段。
2. 中间产物（入口/参数）扫完即丢 —— 在 Scan 阶段 3/8 顺手收集进
   collector，不重跑爬取；扫描成本预期增量 <1%。
3. audit 孤岛 —— 不把 audit 塞进 engine（保持白盒独立入口），关联在
   correlate 层做（P4），两边各自产出实体再缝合。这比"扫描时顺带
   审计源码"更诚实：黑盒目标≠有源码。
4. store 无版本 —— history.json 保持原样（3.0 兼容），graph 数据族
   自带 schema 头；未来再考虑整体 v2。

### P1 数据模型与 Schema（internal/model）

- 新增：`internal/model/ids.go`（确定性内容哈希 ID：`ep_<h12>` /
  `vn_<h12>` / `ev_<h12>` / `df_<h12>`…同一天事实重扫 ID 稳定，ML 可
  跨扫描聚合）、`graph.go`（ScanGraph 容器）、`schema.go`
  （`SchemaVersion = "sitelens.graph/v1"`，JSONL 首行 header：
  schema/generated_at/scan_id/entity）、九类实体文件（entry_point/
  vuln_node/evidence/evidence_link/dataflow/cwe_rel/chain_node/
  chain_edge/priv_change/impact）。
- 数据结构要点：vuln_node{origin: blackbox|whitebox, check_id, cve,
  url, param, severity, verdict, evidence_ids[]}；evidence{kind: request/
  response/snippet/signals/payload/replay, body}；evidence_link{
  blackbox_vuln_id, whitebox_dataflow_id, basis: url|param|tech|manual,
  confidence}。
- 测试：ID 确定性 golden、JSONL 读写往返、schema 头断言。
- 回滚：纯新增包，零风险。

### P2 黑盒结果结构化（engine 收集层）

- 测试：适配器等价性、单测（构造 Crawl/Hit 样本）、DVWA 靶场冒烟
  断言 graph 实体数量与 Finding 数一致。

### P3 白盒 AST / Data Flow

- 前置 spike：tree-sitter CGO 构建（Windows 本机 + CNB CI 各一次），

### P4 黑白盒 Evidence 关联（internal/correlate）

### P6 Attack Chain（证据驱动第一版）

- 新增：internal/chain——只允许三类**真实证据边**：
  ① 同 host 发现的攻击面时序链（信息泄露→入口→注入→影响，全部节点
  必须有 vuln_node 支撑）；② exploit proven/observed 的 impact 边；
  ③ P4 的 evidence_link 边。不做规则臆造、不凭 CVSS 推路径。
- 数据结构：chain_node{kind: recon|entry|exploit|impact, ref_id}、
  chain_edge{from,to,kind,derived_from[evidence_ids]}。
- 测试：靶场全流程（DVWA apocalypse 冒烟）断言链结构含真实节点。
- 回滚：纯新增分析层，可整体关闭。
