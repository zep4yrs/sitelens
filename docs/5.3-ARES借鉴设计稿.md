# 5.3 借鉴 ARES：目标导向证明链与编排安全设计稿

> 状态：设计稿 v1（2026-11-10）
> 参考：[Mafifrizi/ARES](https://github.com/Mafifrizi/ARES)（MIT）——授权红队演练编排平台。
> 本文只借鉴**设计思想与产品叙事**，不引入其 AD/凭据/外溢类攻击模块，不引入 Python 技术栈。
> 原则：默认行为零变化；不增加默认请求量；不改变“授权目标 + 限速 + 不影响被扫描机器”的红线。

---

## 1. 背景与目标

SiteLens 5.2.3 已经能把“可能”变成“确认”：42 条内置无害验证、二次确认、WAF 拦截不判定、
每条发现带复现证据、黑盒发现可与白盒污点通过 `evidence_link` 关联成攻击链。

ARES 的差异化不在“更多漏洞类型”，而在**把多个已验证点串成一条可复核的“打穿路径”**：

- 以目标为导向（如 `domain_admin`）反向合成多阶段路径；
- 只报告“实际打通的链”，每跳带证据；
- 攻击图 DAG 上算最短路径、瓶颈点、横向可行性；
- 用范围围栏（ScopeGuard）与 OPSEC 档位保证“可控、可审计”。

5.3 的目标：**在 Web 授权评估的边界内，把 SiteLens 从“发现列表”升级为“可复核的证明链”**。

非目标：

- 不做内网 AD/Kerberos/凭据窃取/数据外溢模块（法律与产品风险越界）；
- 不做 LLM 全自主规划（保持人在环；MCP/辰极只做“建议 + 确认”）；
- 不重写前端技术栈（继续原生 HTML/JS + Go）。

## 2. 现状盘点（避免重复造轮子）

| 能力 | SiteLens 现状 | 位置 |
|---|---|---|
| 验证型 check | 42 条（本次扩容至 60 条，扩展集仅“全面”档运行） | `internal/checks` |
| 二次确认/回显剔除/软 404 | 已有 | `internal/checks/runner.go` |
| 证据链（请求/响应片段） | 已有 `HitResponse` | `internal/checks`、`internal/model` |
| 黑白盒关联 | `evidence_link` | `internal/model`、`internal/engine` |
| 事实图/攻击链 | `entry_point`/`vuln_node`/`evidence`/`cwe_rel`，graph 默认开 | `internal/model/graph.go`、`web/chain.html` |
| 利用级无害验证 | 四通道（已发布 3.0） | `internal/engine/exploit*` |
| 传输层 SSRF 防重绑定 | 一次解析 → 全量校验 → 按已校验 IP 拨号 | `internal/httpx/client.go`（`Resolve`） |
| 应用层范围白名单 | `scan.allow_hosts`（零请求拒绝越权目标） | `internal/engine` |
| MCP 接口 | stdio，13 工具 | `internal/mcp` |
| 报告 | JSON/CSV/宽表/HTML/MD/SARIF/合规 | `internal/server`、`internal/audit` |

缺口（5.3 要补）：

1. **没有“目标”概念**：结果是扁平发现列表，没有“到某个目标的最短证明路径”；
2. **链只是关联展示**：没有“每跳证据是否充分”的证明等级；
3. **范围围栏只有应用层**：拨号层只做 SSRF 校验，不校验 `allow_hosts`；
4. **MCP 危险操作无确认**：Agent 可直接触发利用级验证；
5. **模板/check 元数据缺失**：没有 ATT&CK 技术编号、OPSEC 噪声等级、安全等级；
6. **验证 check 数量偏少**：60 条相对 ARES 66 模块仍少，且缺系统化转译管线。

## 4. 详细设计

### 4.1 目标导向证明链（核心）

#### 4.1.1 目标模型

```go
// internal/proof/goal.go
type GoalKind string

const (
    GoalAdminTakeover GoalKind = "admin_takeover" // 获取管理员会话/后台权限
    GoalDataExposure  GoalKind = "data_exposure"  // 读取敏感数据（导出/备份/用户表）
    GoalCodeExecution GoalKind = "code_exec"      // 命令执行/RCE
    GoalAuthBypass    GoalKind = "auth_bypass"    // 绕过认证访问受保护资源
)

type Goal struct {
    ID       string   `json:"id"`
    Kind     GoalKind `json:"kind"`
    Target   string   `json:"target"`   // 授权目标（host[:port]）
    Accepts  []string `json:"accepts"`  // 可接受为“达成”的发现类型/check ID
    MaxHops  int      `json:"max_hops"` // 默认 4，上限 6
    Enabled  bool     `json:"enabled"`
}
```

目标由用户在扫描前选择（或由 MCP 建议、用户确认），**不默认启用**。

#### 4.1.2 证明链模型

```go
type ProofLevel string

const (
    ProofProven    ProofLevel = "proven"    // 每跳都有可复核证据，且链首尾可复现
    ProofLinked    ProofLevel = "linked"    // 有证据但存在推断跳（如版本→CVE）
    ProofUnproven  ProofLevel = "unproven"  // 仅路径可行，证据不足
)

type ProofHop struct {
    From     string       `json:"from"`     // 节点 ID（entry_point/vuln_node/asset）
    To       string       `json:"to"`
    Via      string       `json:"via"`      // check ID / 漏洞 ID / 证据 ID
    Evidence []EvidenceRef `json:"evidence"`
    Level    ProofLevel   `json:"level"`
}

type ProofChain struct {
    ID       string     `json:"id"`
    GoalID   string     `json:"goal_id"`
    Target   string     `json:"target"`
    Hops     []ProofHop `json:"hops"`
    Level    ProofLevel `json:"level"` // 取最弱一跳
    Score    float64    `json:"score"` // 0-100，路径置信度（非 CVSS）
    Created  time.Time  `json:"created"`
}
```

#### 4.1.3 路径规划

输入：现有事实图（`entry_point` / `vuln_node` / `evidence` / `cwe_rel` / 资产节点）。
算法：在图上做**受限 BFS/最短路**（边权 = 1 - 置信度；跳数上限 `MaxHops`），

- 起点：入口点（URL/端口/资产）；
- 终点：`Goal.Accepts` 命中的发现（如“后台会话”“敏感数据导出”“命令执行证据”）；
- 边：已有 `evidence_link` / CWE 关系 / 同目标资产关系；
- 剪枝：无证据的推断边降级为 `linked`，不参与 `proven` 链。

输出：Top-N 路径（默认 3 条），每条给出 `Level` 与缺失证据（`missing_evidence[]`）。

#### 4.1.4 报告与 UI

- 结果页新增「证明链」页签：链列表 + 每跳证据 + 缺失证据提示；
- 报告（HTML/MD/JSON/SARIF）增加 `proof_chains[]`，`proven` 链单独标注；
- 工作台增加「目标」选择（默认“不设定目标”＝现有行为）。

#### 4.1.5 安全与默认行为

- `proof.enabled=false` 时完全不规划、不发请求；
- 规划只读图数据，不触发扫描；
- 链中证据沿用现有脱敏规则（不落凭据值/敏感头）。

### 4.2 攻击图路径视图

- 复用 `web/chain.html` 与 graph 数据，新增：
  - 最短路径高亮（到选中目标）；
  - 瓶颈点（多条路径共享节点）标注；
  - 证据缺口节点（无 evidence 的边）虚线显示；
- 只读渲染，不改扫描行为。

### 4.3 ScopeGuard 双层（P0）

现状：`scan.allow_hosts` 应用层零请求拒绝；`httpx` 拨号层做 SSRF IP 校验（`Resolve=true`）。

补强：

1. `httpx.ClientOptions` 增加 `AllowedHosts []string`（来自 `scan.allow_hosts`）；
2. `dialContext` 内对**最终拨号地址**再做一次 allow_hosts 校验（host 规范化 + 端口）；
3. 解析失败/空 IP 集合 → fail-closed 拒绝；
4. 重定向逐跳已校验（现有 `GetFollow`），补 allow_hosts 检查；
5. 非 HTTP 协议层（`internal/netx`）同样在 `Dial` 入口校验 allow_hosts。

默认开启（安全增强），对既有授权扫描无行为变化；未配置 `allow_hosts` 时等价现状。

### 4.4 MCP 危险操作确认（P0）

现状：MCP 13 工具可直接调用利用级验证/扫描。

补强：

1. 工具分级：`read_only` / `active` / `dangerous`（利用级验证、批量、改配置）；
2. `dangerous` 调用必须携带**单次 HMAC 确认令牌**（服务端生成、一次性、绑定工具+参数哈希+TTL 60s）；
3. Pre-flight 范围检查：目标必须命中 `allow_hosts`（未配置则拒绝 dangerous）；
4. 审计日志：工具名/参数哈希/确认令牌 ID/结果，不落敏感值；
5. 防提示注入：工具返回内容标注 `untrusted`，不进入规划器上下文。

### 4.5 OPSEC 噪声档位 + 模板元数据（P2）

- 扫描档位扩展为 `stealth` / `evasive` / `balanced` / `noisy`（现有 fast/standard/full 映射到噪声维度）；
- 每条 check/模板增加元数据：`attck`（技术编号）、`noise`（low/medium/high）、`safety`（read_only/active/exploit）；
- 默认 `balanced`，与现有 ≤8 req/s 红线一致；
- `stealth` 只跑 `read_only + noise=low`。

### 4.6 验证 check 扩容（已做 42→60→113→1010）

- 本次新增 18 条强判据扩展集 check（`.git/config`、`.git/logs/HEAD`、`.env.local/.production`、
  `backup.sql`、`actuator/heapdump|health|mappings`、`swagger.json`、`openapi.json`、`v3/api-docs`、
  GraphQL 内省、K8s `/version`、`/api/v1/namespaces`、Docker Registry `/v2/`、`nginx_status`、
  `phpmyadmin`、GitLab 登录页）；
- 全部 `Lv=1`（仅“全面”档运行），默认扫描请求量不变；
- **模板转译管线（已落地）**：`tools/tpl2check` 从 afrog / nuclei 模板池提取「GET + 静态路径 +
  强判据」模板，过滤 payload/变量/DSL/CVE 复现类，并用通用页面样本做零误报自检，生成
  `internal/checks/tpl_generated.go`（53 条，含 K8s API、Jolokia、Couchbase、Graylog、
  .env.example、php.ini、WEB-INF/web.xml、WPE 配置等暴露面）；门禁见
  `internal/checks/builtin_test.go`（Lv/路径/强特征/ID 唯一/通用页面零命中）；
- 当前内置验证总数：**1,010 条**（60 手写核心 + 167 手写扩展 + 783 转译）。
- 结构性门禁：`internal/checks/builtin_test.go`（ID 唯一/路径/条件/字段/Lv 断言）。

后续路线（5.3 内可选）：

1. 从 afrog（1,699 条）/nuclei 模板池转译强判据 check，人工复核后入扩展集；
2. 目标：100+ 条验证 check，全部带 ATT&CK 与噪声元数据；
3. 误报门禁：每条新 check 必须在软 404 靶场 + 2 个正常站点上零误报。

### 4.7 就地升级保证（P2，可选）

- 升级包清单（manifest）含文件 SHA256 与“不可覆盖白名单”（`state/`、`pools/`、`plugins/`、
  `data/wordlists/`、用户配置）；
- 升级前校验、失败回滚到上一版本目录；
- 与现有 `update-seed` 版本化种子交付衔接。

## 5. API 设计（草案）

```
POST /api/proof/goals        创建目标（需授权目标）
GET  /api/proof/goals        列出目标
POST /api/proof/plan         对目标规划路径（只读，返回 ProofChain[]）
GET  /api/proof/chains       列出证明链（可按 goal/level 过滤）
GET  /api/graph/paths?to=    图路径（最短/瓶颈/证据缺口）
```

所有写接口要求 `allow_hosts` 命中；`plan` 为只读、幂等。

## 7. 验收标准

- 默认配置下扫描行为与 5.2.3 完全一致（请求数、判定、报告字段 additive）；
- `proof.enabled=true` 时只读规划，不新增请求；
- ScopeGuard：越权目标在应用层与拨号层均零请求拒绝（靶场用例）；
- MCP：dangerous 工具无令牌必拒绝，令牌重放必拒绝；
- 单测/靶场/`-race` 全绿；新增 check 在软 404 靶场零误报；
- 报告新增字段向后兼容（旧字段不变）。

## 8. 明确不做

- AD/Kerberos/凭据转储/数据外溢模块；
- LLM 自主多步执行（无人工确认）；
- 突破限速红线的“快速打穿”模式；
- 修改既有证据/报告字段语义。
