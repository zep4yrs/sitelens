## 1. 4.0 定位

SiteLens 4.0 的定位是 **能力升级 + 架构边界强化**，不是重写：

> **从「单点漏洞验证」升级为「黑白盒安全分析 + 攻击链还原」。**

- **升级**：在 3.0 已有的黑盒检测（指纹 / 模板 / DAST / 利用级验证 / 情报关联）
  之上，补齐**结构化事实抽取**、**白盒源码分析**、**黑白盒证据关联**、
  **证据驱动的攻击链建模**，为 5.0 ML 提供结构化真实安全关系数据。
- **强化边界**：把「检测能力」与「数据模型 / 存储 / API」分层解耦，
  明确 Frontend → REST API/Service → Core Engine → Analyzer → Store 的依赖方向，
  让每条能力有稳定的数据边界，而不是继续堆在无类型的 map 上。
- **不做**：不推倒 3.0 重写；不引入微服务；不为架构漂亮而重构。

4.0 结束时应同时满足两条主线的验收（资源指标 + 安全分析能力），并在同一
Pipeline 中汇合。

## 2. 4.0 总体目标

按用户要求的目标结构（每条向下依赖上一条的事实）：

```
Entry Point
  ↓
Endpoint / Parameter
  ↓
Finding
  ↓
Evidence
  ↓
Source / Sink
  ↓
Data Flow
  ↓
Vulnerability / CWE
  ↓
Attack Chain
  ↓
Privilege Change
  ↓
Impact
```

总体目标分两组：

**Track B（安全分析）**

1. 黑盒结果结构化：把当前扫描的瞬时产物（入口 / 参数 / 发现 / 证据）变成可持久化实体。
2. 白盒源码分析：真实 AST、source/sink、函数与调用关系、函数内数据流。
3. 黑白盒证据关联：黑盒发现 ↔ 白盒数据流的 evidence_link。
4. CWE 关联：白盒规则 / 黑盒 check ↔ CWE，CVE ↔ CWE。
5. 攻击链建模：**仅凭真实证据**建链，不臆造路径。
6. Privilege Change 与 Impact 实体化。
7. 统一数据模型 + Schema 版本化 + graph JSONL 落盘与导出。
8. 4.0 → 5.0 ML 的结构化事实接口（只输出事实，不回灌执行链）。

**Track A（资源治理）**

9. 把引擎空闲 RSS 从 ~1 GB 降到 ≤ 300 MB，full 档峰值 ≤ 800 MB，
   GUI 合计 ≤ 250 MB，扫描时长回退 ≤ 5%（详见第 5、21 节）。

### 3.4 依赖方向（import 实测）【已存在】

```
server → engine, store, audit, intel, config, ...   （装配层，允许宽依赖）
store  → engine                                     （ScanRecord 内嵌 engine.Result）
engine → dast, checks, crawler, intel, modules, ... （不 import store / 不 import audit）
audit  → config                                     （独立孤岛，引擎从不 import）
model(4.0 新增) → 无依赖叶子包（规划）
```

两个对 4.0 关键的结构性事实：

1. **白盒（audit）与黑盒（engine）今天完全无连接**——没有共同数据模型、
   无互相引用、也不在同一条命令流水线里。
2. **store 依赖 engine（不是反向）**，engine 不知道存储存在。4.0 图数据
   落盘应是 `store → model`，而不是让 engine 学会写盘。

## 5. Track A 资源治理路线

> 本节完整保留原 `开发文档-4.0.md` 内容（实测基线 / 瓶颈分析 / 目标 / 方案分层 /
> 验收口径 / 已落地前置变更），无删减。

### 5.1 实测基线（2026-09-13，本机 Windows 11，任务管理器 / Process 口径）【已存在】

| 进程 | 常驻内存（RSS / Private） | 说明 |
|---|---|---|
| sitelens.exe（引擎，空闲） | **977 MB / 1011 MB** | 刚启动未扫描的基线，不是峰值 |
| sitelens.exe（引擎，扫描中峰值） | ~1500 MB（实测 1,522,224 K） | full 档扫描期间 |
| SiteLens（Electron 壳） | 4 进程合计 ~410 MB | main + gpu + renderer + utility |
| **合计** | **常驻 ~1.4 GB** | 引擎是大头 |

结论：引擎空闲基线 ≈1GB 是主要矛盾——扫描还没开始，内存已经上去了。

### 5.2 瓶颈分析（代码证据）【已存在的问题】

1. **情报库全量常驻解码（主因）**：`internal/intel` 启动时把 `nvd_cves.json.gz`
   （磁盘 37MB 压缩）全量解码为 `[]NVDEntry` 常驻——描述全文、CPE 产品向量全是
   Go string，解码后膨胀 20~30 倍；kev / cve_ms / tscan 索引同模式。指纹扫描
   （多数日常场景）根本用不到 NVD 全表，却为它常年买单。
2. **无 GC 软上限**：全仓无 `SetMemoryLimit`/`GOGC` 调优，Go 默认堆翻倍增长策略
   把扫描期尖峰进一步放大。
3. **nuclei 模板池**：apocalypse 档 cap 6000 模板，编译期内存尖峰 + 每次扫描重新
   编译（无跨扫描缓存）。
4. **并发上限分散**：crawler / DAST / 主动模块各有自己的并发键（`MaxConcurrent: 3`
   等），没有全局内存预算约束，档位叠加时互相放大。
5. **Electron 壳 4 进程**结构固定 ~0.4GB，属于 Chromium 底价，优化空间有限但可挤
   （renderer 定时器降频等）。

### 5.3 量化目标【计划开发，验收口径】

| 指标 | 现状 | 4.0 目标 |
|---|---|---|
| 引擎空闲 RSS | ~1.0 GB | **≤ 300 MB** |
| 引擎扫描峰值（full 档） | ~1.5 GB | **≤ 800 MB** |
| GUI 合计 | ~0.4 GB | **≤ 250 MB** |
| 扫描时长 | 基线 | **不回退超过 5%** |

### 5.4 方案分层

**Quick Wins（3.x 可带 / 4.0 早段，风险低）【计划开发】**

- **A1 GC 软上限**（✅ 已实现 2026-09-14，见 26.21）：引擎启动时
  `debug.SetMemoryLimit(1 GiB)` + `debug.SetGCPercent(70)`（`internal/resource`）。
- **A2 NVD 字段瘦身**（✅ 已实现 2026-09-14，见 26.23）：`NVDProd` 只留 `VP`
  （版本边界字段经全仓核实无消费方）——full 峰值 934MB → **796MB，已达标**。
- **A3 惰性加载**（✅ 已实现 2026-09-14，见 26.22）：NVD 首次触达才解码；
  **实测空闲 RSS 977MB → 129MB，已达标**（≤300MB）。
- **A4 归还 RSS**（✅ 已实现 2026-09-14，见 26.21）：扫描结束调 `debug.FreeOSMemory()`，
  把堆还给 OS，任务管理器立即可见回落。

**中期（4.0 主力）【计划开发】**

- **A5 情报库列式快照**：自建只读 mmap 索引（按 CVE 随机访问）替代全量解码常驻；
  更新管线照旧，加载成本 O(1)。
- **A6 nuclei 模板编译缓存**：进程级 LRU，跨扫描复用编译产物（apocalypse 重复
  扫描收益最大）。
- **A7 全局内存预算器**：`engine.max_memory_mb` 配置 + 超限自动降档
  （模板 cap → 爬取页数 → DAST 参数数，逐级收缩并在事件流明示降级）。
- **A8 结果流式落盘**：大目标的 Verified/Pages 改为流式写库，不再整包聚合在
  内存 map。

**GUI 侧【计划开发】**

- **A9** renderer 图表/轮询定时器在窗口不可见时降频（已有 `backgroundThrottling`，
  补齐自研轮询点）；可选关闭 GPU 加速的开关（设置 → 桌面端）。

**长期【未来方向】**

- **A10 引擎 / 情报库进程分离**：情报库独立 sidecar 进程 + IPC 查询，扫描进程
  随任务退出全量释放；空闲态只剩情报库常驻（瘦身后的百 MB 级）。

### 5.5 验收口径

## 11. Privilege Change（P7）

## 18. 多语言方案

**Go 主干不动摇**。4.0 全部编排 / 存储 / API / 关联 / 链建模在 Go 内完成；
现有黑盒资产、零依赖单二进制纪律、桌面安装器 / CI / AV 规避都绑定了这个形态。

**AST 解析器是唯一可能引入第二语言的点**，候选与裁定：

- **方案 A（推荐先试）**：tree-sitter 官方 Go 绑定（CGO）。语法全
  （py/js/php/java/go），进程内无 IPC。代价：Windows 本机构建需 gcc 工具链、
  CI 产物特性变化需重验 AV 白名单、go.sum/vendor 面变大。
- **方案 B（A 证伪后备）**：Rust 分析器 sidecar（独立 exe + JSONL 文件协议）。
  解析生态最好，但破坏单二进制、安装器双 exe、协议要版本化。
- **方案 C（否决）**：纯 Go 解析器——Python 侧无维护良好的实现
  （audit.go 头注释已实证此判断），不可行。

**裁定**：**P3 第一步做方案 A 构建 spike（本机 + CI 各一次）；
CGO 成本被证伪才引入 Rust，且分析器输出统一走 graph JSONL schema——
语言切换被 schema 边界隔离，不波及其他层**。
**不为「多语言」强行引入 Rust**；Python 只属 5.0 ML、只读 graph JSONL
（现状已满足：python 分支独立文件夹）。

### 18.1 P3 构建 spike 结论（2026-09-14，实测）【已执行】

**结论：方案 A（tree-sitter CGO）通过，不引入 Rust。** 证据如下（全部实测）：

| 验证项 | 方法 | 结果 |
|---|---|---|
| 依赖可获得 | `goproxy.cn` 拉 `github.com/smacker/go-tree-sitter` | ✅ 成功（国内镜像可达） |
| 原生 CGO 构建 | WSL archlinux gcc 16.1 + `CGO_ENABLED=1 go build` | ✅ 成功 |
| **真实 AST 解析** | Python 源码 `import os / def f(): x=input(); os.system(x)` | ✅ 产出 `module → import_statement + function_definition`，可取函数体 |
| 5 语言 grammar | python/javascript/php/java/golang 一次性加载 | ✅ 全部可用 |
| Windows 交叉编译 | `GOOS=windows CC=x86_64-w64-mingw32-gcc` | ✅ 产出合法 **PE32+ x86-64** |
| **Windows 原生运行** | 把交叉产物拷到 Windows 直接执行 | ✅ 正确解析 AST（非仅编译通过） |
| vendor 体积 | 1 grammar vs 5 grammar | 4.1MB/15 个 C 文件 vs 16MB/21 个 C 文件 |
| Windows 本地 CGO | 本机 `CGO_ENABLED=1 go build runtime/cgo` | ❌ **无 gcc**（本机未装 C 工具链） |

**关键环境事实（决定集成方式）**：

- 本机 Windows **没有任何 C 编译器**（`gcc/cc/clang/cl` 均不在 PATH），
  `go env CGO_ENABLED = 0`；因此**当前状态下 Windows 本地无法构建 CGO 包**。
- WSL archlinux 有 gcc 16.1 + glibc 2.44，CGO 与 Windows 交叉编译均可用。
- CI 基础镜像 `golang:1.26.8` = Debian bookworm（含 gcc；且流水线已在跑
  `go test -race`，说明 CI 本就有 CGO 能力）；交叉编译需补装
  `gcc-mingw-w64-x86-64`（提供 `x86_64-w64-mingw32-gcc`）。
- `desktop/build-engine.js` 的 `go build` **未设 GOOS/CGO**，即按执行机宿主平台
  构建。本机 Windows 发布路径下默认产出 Windows exe——**这是 CGO 集成的真正
  约束点：跑 `npm run engine` 的那台机器必须有目标平台的 C 工具链**。

**因此方案 A 的落地前置**（二选一，见 18.2）：Windows 侧装 mingw-w64/MSYS2；
或把 AST 包用 `//go:build cgo` 隔离（无 CGO 时优雅降级，CI/发布机带工具链构建）。

### 18.2 待定：CGO 集成方式（需拍板）

| 选项 | 做法 | 代价 |
|---|---|---|
| **A1 全平台 CGO** | Windows 本机装 MSYS2/mingw-w64，`CGO_ENABLED=1` 常开 | 开发者机器需装工具链；vendor +16MB；AV 需重验 |
| **A2 build tag 隔离**（推荐） | `internal/astx` 用 `//go:build cgo` + 纯 Go 桩；无 CGO 时 AST 能力优雅关闭，带工具链的机器（CI/发布机）构建完整能力 | 无 gcc 的机器本地无法测 AST（CI 覆盖）；需在 `build-engine.js` 显式设 `CGO_ENABLED=1` |
| A3 Rust sidecar | 方案 B | 破坏单二进制，暂不采 |

**推荐 A2**：最小改动、不破坏现有 Windows 本地 `go build ./...`、可随时回退；
代价是 AST 的本地开发需在 WSL 或装 gcc 后进行。

## 25A 源码审计升级设计：Monaco Editor + 文件树 + 错误标注联动（2026-09-16 设计，待实施）

> 状态：**设计定稿，未实施**。实施前不再变更布局语义；如需改动先改本节。

### 25A.1 目标与范围

把源码审计从「上传 → 表格结果」升级为 VS Code 式体验：

1. **文件树**：上传的文件 / zip 解包后的相对路径按目录树展示，点击文件在编辑器中打开；
2. **Monaco Editor**（VS Code 同款编辑器内核，官方 min 发行版）：按扩展名语言高亮（python/javascript/php/go/sql/html/css/json 等）；
3. **错误标注联动**：审计 findings 按 `file:line` 投射进编辑器（波浪线 + 行号侧标记 + 行背景），severity 映射 红=high/critical、黄=medium、蓝=low；点击「审计发现」列表某条 → 编辑器打开对应文件并跳行居中高亮。

范围外：不改动审计引擎规则与 AST 分析本身；不改动其余四个工作台模式。

### 25A.2 布局与交互

```
┌─────────┬──────────────────────────────┐
│ 模式行   │  Monaco Editor（错误标注）     │
│ ──────  │  12├ password == "admin123"  │
│ 拖拽上传 │                              │
│ 文件树   │  ──────────────────────      │
│ ├ app.py│  审计发现列表（可折叠，点击跳行）│
│ ├ lib/  │                              │
│ └ main.js│                             │
│ ──────  │                              │
│ ▷开始审计│                              │
└─────────┴──────────────────────────────┘
```

- 左控制列（302px，审计模式）：**拖拽上传区（收纳为一行高度，点击/拖入均可）→ 文件树（填充剩余高度，可滚动，空态=拖拽引导）→ ▷ 开始审计**。文件树不新开画布列。
- 画布：Monaco 主体 + 底部可折叠「审计发现」面板（默认展开，徽章沿用全局 severity 配色）。
- **删除「载入演示样本」**：前端按钮与 runDemo() 整删；后端 `/api/audit/demo` 保留但无任何 UI 入口（实施时如确认无测试引用则连后端一并删除）。

### 25A.3 数据流与接口

`POST /api/audit`（multipart files）响应在现有字段基础上扩展：

```json
{
  "files": 3, "lines": 421, "findings": [...], "by_severity": {...},
  "sources": ["app.py", "lib/db.php", "main.js"],
  "contents": { "app.py": "def login():\n  ...", "lib/db.php": "..." }
}
```

- `sources`：zip 解包后**全部文本文件**的相对路径（树的数据源）；
- `contents`：单文件 ≤ **512KB** 且探测为 UTF-8 文本（无 NUL 字节）才携带；二进制 / 超大文件只进 `sources`，前端树中置灰、点击提示「仅审计线索，无预览」；
- **隐私承诺不破**：内容仅随响应回传用户浏览器，服务端仍审计后即删、不落盘、不做会话缓存。

### 25A.4 前端模块设计

- **Monaco vendor**：`web/monaco/`（官方 min 发行版整体入仓，go:embed 随引擎分发，约 15MB；仓库已有 47MB packs 先例）。页面零构建集成：`require.config({ paths: { vs: "/monaco/vs" } })` 标准 loader；**审计模式首次激活才注入 loader 脚本**（懒加载）。
- **文件树**：由 `sources` 路径列表构建目录树（纯函数，可单测）；节点点击 → 打开对应 model；目录可折叠。
- **编辑器生命周期（与 Turbo 共存）**：models 单例常驻 JS 侧（Monaco model 与 DOM 分离，切模式不丢状态）；editor 实例随画布 DOM 重建时 dispose 后重建（开销毫秒级）；重入画布后调用 `editor.layout()` 修正尺寸。
- **标注联动**：`setModelMarkers`（owner="audit"）+ `deltaDecorations` 行背景；发现面板条目点击 → 打开文件 model → `revealLineInCenter` + 1s 高亮装饰。
- **语言映射**：按扩展名映射 monaco language；未知扩展按纯文本。

### 25A.5 后端改动

- `internal/server` 审计 handler：响应追加 `sources` / `contents`（文本探测 + 512KB 上限，常量可配）；
- `/api/audit/demo`：保留、无 UI 入口（视实施时引用情况决定是否删除后端）。

### 25A.6 边界与风险

| 风险 | 对策 |
|---|---|
| Monaco 体积撑大仓库/二进制 | min 版约 15MB 入仓（packs 47MB 先例）；后续可裁剪非审计语言 |
| 超大 zip / 上千文件 | 树虚拟化不做（工作台场景文件数有限）；contents 只带 ≤512KB 文本 |
| display:none 下初始化测量失真 | 切入审计模式后再 `editor.layout()` |
| CDN 依赖 | 无——Monaco 全本地路径，符合零外部依赖纪律 |

### 25A.7 验收清单（CDP 实测）

1. 上传多文件 zip → 树层级与解包路径一致；
2. 点树文件 → 编辑器内容 + 语言高亮正确；
3. findings 标注行数与发现列表一致，severity 颜色正确；
4. 点发现条目 → 编辑器跳行居中 + 高亮；
5. 切走审计模式再切回 → 文件树与编辑器状态保留；
6. 页面内不存在「载入演示样本」入口；
7. 全链路 Turbo 验证不回退（既有 VERIFY-PASS 仍通过）。

### 26.21 指纹误判修复 + Track A 启动（A1/A4）（2026-09-14）

**A. 修复：指纹关键词通道造成大量误判（用户发现）**

- **现象**：用户质疑「DVWA 真的有那么多技术？」——实测单站被判 **58 项技术**，
  逐条核对证据后确认**只有 4 项是真的**（Apache 2.4.68 / PHP 8.5.10 / Debian /
  DVWA），其余 **54 项全是假阳性**。
- **根因**：EHole 类社区指纹是「**任一关键词命中即算**」的 OR 语义
  （`internal/sitelens/fingerprint.go` 的字面量通道命中即 return），而导入的
  关键词里混有大量通用词：`login` / `username` / `password` / `User` /
  `Application` / `login.php` / `type="password"` / `must-revalidate`。
  于是任何带登录表单的页面都会命中几十个无关产品。
- **修法（数据驱动、可审计）**：新增 `internal/sitelens/weakkw.go`——
  把关键词按语义 token 拆分（ASCII 字母数字段 / 连续 CJK 段 / 扩展名归通用），
  若**全部 token 都是通用词**则判为**弱证据**；字面量通道要求至少一个**强关键词**
  命中才算识别（只有弱命中不返回，继续尝试其它通道）。作用于 html 字面量通道与
  通配 header 通道（后者曾把 `SAMSUNG-SNB-2000` 判在无关联站点上）。
  正则通道（Wappalyzer 精编）不受影响。
- **验证（实测）**：同靶站 **58 项 → 4 项**，正好是真阳性；新增
  `weakkw_test.go` 3 项（分词 / 强弱判定 / DVWA 误判回归）。
- **影响面**：这是**精度修复**，会减少技术识别数量（识别更准）。对依赖技术清单的
  情报关联，误判减少同时也会减少由假技术带来的**假情报关联**（净收益）。

**B. Track A 资源治理启动：A1 + A4**

### 26.22 Track A：A3 惰性加载（空闲 RSS 977MB → 129MB，达标）（2026-09-14）

**实测定位主因（推翻原先假设）**：原开发文档判断主因是「情报库全量常驻解码
（intel_dump）」。实测逐项测量后修正：

| 阶段 | HeapSys |
|---|---|
| baseline | 3.9 MB |
| `intel.Load`（intel_dump 1.3MB gz） | 66.8 MB |
| **`LoadNVD`（nvd_cves 37MB gz）** | **1681.6 MB** |

即**主因是 NVD 全量索引（30 万+ CVE，≈1.7GB HeapSys）**，而非 intel_dump。

**A3 实现**：把 NVD 从「启动即全量解码」改为**惰性**——
`KB.AttachNVDPath(path)` 只记路径；`nvdStore()`（`sync.Once`）在首次真正取数时
解码。关键细节：**`HasNVD` / `NVDCount` 不触发加载**（存在性判断不能把索引拉起来），
只有读数据（`nvdFill` 补 CVSS/CWE、CPE 检索、用户主动搜 NVD）才加载。
`internal/engine` 的 CVE→CWE 判断改用 `HasNVD`。

**A3 收益（实测）**：

| 场景 | HeapSys |
|---|---|
| intel.Load + 惰性挂路径 | **71.0 MB** |
| 调 HasNVD/NVDCount（判断） | **71.0 MB**（不加载） |
| 真正取数 `NVD()` | 1715.2 MB |

**端到端（`serve` 空闲 RSS，任务管理器口径）**：

| | RSS |
|---|---|
| 原基线（开发文档实测） | **977 MB** |
| **A1 + A3 后** | **129 MB**（132,032 K） |

**量化目标达成**：空闲 RSS ≤ 300MB —— **实测 129MB，达标（降幅 ≈87%）**。

**测试**：`TestNVDPathLazyLoading`（挂路径不加载 / 判断不触发 / 首次取数才解码 /
幂等）、`TestNVDFillTriggersLazyLoad`（补全路径自动触发）。全量回归绿。

**真实扫描验收**：DVWA 实扫功能不受影响（4 项真技术 + 47 条情报）。

**Track A 进度**：A1 ✅ / A3 ✅ / A4 ✅；A2（NVD 字段瘦身，收益被 A3 覆盖大半）、
A5-A10 待续；**full 档峰值 ≤800MB 与 GUI ≤250MB 尚未实测**。


### 26.23 Track A：A2 NVD 字段瘦身（full 峰值 934MB → 796MB，达标）（2026-09-14）

**依据（实测组成分析）**：NVD 索引 372,542 条、3,039,149 个 CPE 约束。
`NVDProd` 原含 6 个 string 字段（96B/条 × 300 万 ≈ **292MB**），是全档峰值的主要构成。

**全仓核实**：`NVDProd` 的**版本边界字段（EE/EI/SE/SI/V）无任何消费方**——
只有 `VP`（vendor/product）被读取（`byProd` 索引、统计检索、update-tplintel）。
版本区间判定由 `vuln_kb` / `affected_ranges` 承担，NVD 侧只做产品名检索。

**A2 实现**：`NVDProd` 瘦到单字段 `VP`（16B/条），同步侧不再写出边界字段；
文件版本 v2 → **v3**（旧 v1/v2 文件用新结构解码完全兼容，未知字段忽略）。

**验收（实测）**：

| 场景 | 峰值 RSS |
|---|---|
| A1+A3 后（未瘦身） | 934 MB |
| **+ A2 瘦身** | **796 MB**（目标 ≤800MB）✅ |

功能不受影响（真实 DVWA 实扫：7 技术 / 47 情报）。

**Track A 量化目标进度（实测）**：

| 指标 | 目标 | 实测 | 状态 |
|---|---|---|---|
| 引擎空闲 RSS | ≤ 300 MB | **129 MB** | ✅ 达标 |
| full 扫描峰值 | ≤ 800 MB | **796 MB** | ✅ 达标 |
| GUI 合计 | ≤ 250 MB | **≈601 MB WS / ≈484 MB private（5 进程）** | ❌ 目标对 Electron 不现实，按实测封存（见 26.24 补充） |
| 扫描时长回退 | ≤ 5% | 未实测（A 系列只减内存，未动扫描逻辑） | ⏳ |

**可恢复性说明**：被瘦身的版本边界字段可从 NVD 源随时重建
（`update-nvd feed`，实测约 5 分钟），属**可恢复的数据精简**而非不可逆丢失。

**Track A 剩余**：A5 列式 mmap 快照 / A6 nuclei 编译缓存 / A7 内存预算器 /

### 26.24 Track A：A5-A10 完成 + Release 重载数据丢失真 bug 修复（2026-09-16）

**A5 情报库惰性解码（原方案「列式 mmap 快照」，实做取简）**：
`KB.LoadLazy(dump, ranges)` 只记路径；`ensureDecoded()`（双检互斥）在首次真正用到
（Match/ServiceFP/FingerDir/统计）才解码；解码前 `AttachTplIntel` 挂起 `pendingTpl`
队列、解码后按序并入。动机：intel_dump 解码占 HeapSys ≈67MB，serve 空闲不必付。
加载失败延迟到使用点（表空态可用），`LoadError()` 可查。

**A6 nuclei 模板编译缓存**：`internal/nuclei/compile_cache.go` —— `LoadFileCached`
带进程级缓存（LRU 上限 + 单飞），apocalypse 等全量模板场景跨扫描复用编译产物；
引擎 `runNuclei` 改走缓存入口。测试 3 项（缓存命中/并发单飞/内容变更失效）。

**A7 全局内存预算器**：`Scan.MaxMemoryMB`（默认 768）——扫描流程三点检查
（深爬前/ nuclei 前/主动模块前）超限逐级降档：爬取页数减半 → 模板上限减半 →
跳过主动模块；全部动作记入 `Extras["budget"]` 并推 `budget` 事件（明示降级，
不静默砍覆盖）。测试：极小预算触发两类降档 + 默认预算不降档。

**A8 页面清单驻留上限（原方案「结果流式落盘」，实做取简）**：
`Scan.PagesRetained`（默认 2000）——爬取后、指纹前裁剪 `res.Pages`，
超出记 `Extras["pages_omitted"]`。报告体积与驻留可控，检测能力不受影响
（指纹/DAST 用的是独立 `pages` 局部变量）。

**A9 GUI 轮询治理**：`web/js/common.js` `slPoll` —— 页面不可见时降频
（document.visibilityState），app/batch/settings 三处接线；窗口隐藏期
请求量大幅下降，renderer 不再空转。

**A10 情报常驻释放（原方案「sidecar 进程」，实做进程内等价）**：
A3+A5 惰性化后无需独立进程——`KB.Release()` 清表复位；`Engine.ReleaseIntel()`
封装；`POST /api/admin/release-intel` 管理端点返回释放前后堆指标
（实测 **86.0MB → 17.0MB**），下次访问自动重载。供长空闲期调用。

**真 bug（A10 验收测试抓出，两处叠加）**：`Release` 后数据永久丢失——
① `Load` 走 `decodeAll` 不记源路径，Release 后 `ensureDecoded` 判定
「纯内存构造」直接空表；② `sync.Once` 只触发一次，复位标记后重解码永不发生
（NVD `nvdOnce` 同病）；③ serve 启动并入的模板情报（29554 行）与 OSV 覆盖
（180 条）重载不重放。**后果**：调用一次 release-intel，之后所有情报匹配
永久残废。**修复**：`Load` 复用惰性骨架保留路径；Once → 双检互斥
（`loadMu`/`nvdMu` + `nvdTried` 可重试）；Release 把负 ID 段模板行存回
`pendingTpl`、最近覆盖存回 `pendingOv`（`lastOv` 记录），重载后经
`ensureDecoded` 原序重放。回归锁 `TestReleaseReplaysTplAndOverrides`。

**测试**：intel `lazy_test.go` 5 项（延迟解码/挂起并入/缺失容错/Release 重载/
重放锁）+ engine `budget_test.go` 4 项 + server `release_intel_test.go`
（端点 200 + released + 堆指标 + 释放后引擎可用）。

**全量回归（2026-09-16）**：`go test ./internal/...` **32 包全绿**；
gofmt/vet 零输出；`node --check` web/js 全过；桌面 `node --test` **25/25**；

**Track A 终态**：A1-A10 **全部完成**。A5/A8/A10 按实测取简（惰性/驻留裁剪/

### 26.25 GUI 换壳实验：Wails v3（2026-09-16）

**背景**：26.24 补充实测确认 Electron 壳全树 ≈601MB WS（≤250MB 目标不可达）；
用户拍板尝试 Wails（Go 后端 + 系统 WebView2，与引擎同语言栈）。

**实验物**：`desktop-wails/`（与 Electron 壳并存，互不影响）——
Wails **v3.0.0-beta.22**，纯 Go 单文件壳，职责对齐 Electron 壳的最小子集：
引擎目录探测（打包态 `engine/` / 开发态 `../desktop/engine` / 环境变量覆盖）→
空闲端口 → 最小配置写**用户目录**（`%APPDATA%/SiteLens-Wails/config.yml`，
EPERM 教训：不写安装目录）→ 拉起 `sitelens.exe serve`（cwd=引擎目录）→
`/api/version` 健康检查 → 窗口直接加载引擎 URL（**引擎与 web/ 全部零改动**）→
退出回收引擎进程。`-hidden` 参数供内存测量（窗口隐藏照常分配）。
构建：`go build -ldflags "-s -w -H=windowsgui"`，产物 **11.9MB 单文件**
（Electron 安装包约 100MB）。

**功能验证**：窗口完整渲染扫描工作台（侧栏/表单/芯片/空状态），引擎 API 200，
WebView2 153 环境（Windows 11 企业版）正常。CGO_ENABLED=0 纯 Go。

**内存实测（同机同引擎对比，任务管理器口径）**：

| 形态 | 进程 | WS 合计 | Private 合计 |
|---|---|---|---|
| Electron 壳 | 5（主/渲染/GPU/网络/引擎） | ≈601 MB | ≈484 MB |
| **Wails 壳全树** | **8（壳/引擎/msedgewebview2×6）** | **≈491 MB** | **≈376 MB** |

降幅 **≈18%（WS）/ ≈22%（Private）**——没有宣传的 50%+，因为 WebView2
渲染树本身就是完整 Chromium 多进程管线（browser/GPU/network/storage/2×renderer
/crashpad），真正省掉的是 Electron 自带的 Node 主进程与冗余 utility。
**碾压项是分发体积**：11.9MB 单文件 vs ~100MB 安装包。

**测量口径说明（诚实记录）**：① 隐藏窗口测量，可见窗口下渲染器内存略高；
② 稳定期 30s（Electron 基线为 60-90s），渲染器缓存偏冷，Wails 数字略偏乐观；
③ 实验期间多次「秒退」为 Git Bash 作业回收 artifact（Start-Process 分离启动
后稳定运行 90s+，shell.log 全程留痕），非产品缺陷，真实用户无感。

**结论（待用户拍板）**：技术可行、内存收益中等（百 MB 级）、分发体积收益大；
但若正式迁移需补齐 Electron 壳已有能力：自动更新（electron-updater 对应
tauri/wails updater 方案）、NSIS 品牌安装器、splash 启动页、托盘、端口策略
与 yml 合并的完整移植。建议与视觉升级统筹决策：Electron 壳已趟平的坑
是真实成本，Wails 的 beta 状态（v3 API 虽官方称稳定）也是真实风险。

## 附 A 开发纪律

1. 所有改动必须基于**当前代码**；不根据旧版本推测。
2. 不虚构功能；不虚构测试结果；不虚构性能数据。
3. 不修改 3.0 核心行为，除非有明确兼容方案（第 19 节）。
4. 每阶段必须有测试；保持 3.0 回归测试通过。
5. 修改 web/desktop 必须走现有构建 / 打包 / 验证流程。
6. 不使用 LLM / RAG / Agent / Multi-Agent 作为 4.0 核心。
7. 5.0 ML 与 4.0 执行链保持边界（5.0 只读 graph JSONL，不回灌）。
8. 不为「多语言」强行引入 Rust（按 P3 spike 裁定）。
9. 不为「架构升级」引入微服务。
10. 不做无意义大规模重构；不推倒 3.0 重写。
11. 攻击链必须证据驱动：无真实 evidence 不成边；不据 CVSS / CVE / 规则名 /
    模型猜测制造攻击路径。
12. 不把 5.0 ML 塞进 4.0 核心。
