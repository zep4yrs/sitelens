# SiteLens 5.2 版本升级规划

> **主题**：检测质量与数据治理 · 让检测更可信、可追溯、可评估
> **副题**：从检测能力的持续积累，迈向检测质量的系统化提升。SiteLens 5.2 围绕**检测质量度量**、**检测数据治理**、**检测回归分析**与**机器学习优化**四个方向持续迭代，进一步提升检测结果的可信度、可追溯性与可评估性。
>
> `SCAN · ANALYZE · SECURE`
>
> **当前状态**：5.2 处于规划阶段。以下内容为**预期的研发方向**，不意味着相关功能已经实现或确定。
> **发布时间**：具体功能范围、实现方式与发布时间，将以实际开发进度和最终发布说明为准。
> **欢迎建议**：欢迎持续关注 SiteLens「晦明」，也欢迎通过项目反馈渠道提出建议。

---

## 一、项目定位升级

从 5.2 版本起，SiteLens 将正式引入中文名称：

<div align="center">

# 晦明 | SiteLens

### 洞察隐患 · 明晰风险

</div>

| 字 | 寓意 |
|---|---|
| **晦** | 寓意幽深而不足，代表**尚未被发现**的问题与潜在风险 |
| **明** | 寓意清晰与明朗，代表通过**检测、分析与验证**，让问题逐步清晰 |

从「发现隐蔽的问题」到「通过检测、分析与验证澄清问题」，**「晦明」不仅是项目各目标的延伸，也体现了 SiteLens 持续提升检测能力与结果可信度的发展方向**。

## 二、四大升级方向

### 01 · 检测质量度量

建立更加完善的检测指标体系，让检测效果从**经验判断**走向**数据化评估**。

- 完善检测结果统计与质量指标
- 评估检测覆盖情况、有效发现与误报表现
- 为不同检测策略的效果对比提供依据

> **本方向已有基础**（5.1 → 5.2 期间完成）：
> - CVSS 计分与官方口径逐条对齐（29 万条 NVD 官方数据对拍，100% 一致）——严重度分是检测结果的关键度量口径
> - 修复"四段版本号被误判为受影响"的判定缺陷——消除误报表现的一类系统性来源
> - 修复"表单复现命令被渲染成 GET"的证据链缺陷——让"可复核"这一质量属性重新成立

### 02 · 检测数据治理

加强检测模板、技术指纹与 CVE 情报之间的**关联管理**，提升安全检测数据的质量与利用效率。

- 优化模板与漏洞情报的关联关系
- 探索重复数据识别与去重机制
- 强化数据来源记录与变更追踪
- 为后续模型训练和检测分析提供更可靠的数据基础

> **本方向已有基础**（5.1 → 5.2 期间完成）：
> - 修复 afrog 模板来源**整体失效**的问题（1,699 条模板的判定表达式此前被静默丢弃，通过率 0%）——恢复一条数据来源的可用性
> - 模板调度新增 CVE 通道（指纹受影响 CVE 反查模板并提权）——模板与情报的关联从"标签匹配"扩展到"CVE 关联"
> - 修复情报覆盖合并时的**原地重排**缺陷——消除数据治理过程中"情报与 CVE 错配"的静默错误
> - 数据资产分层交付与来源标注（`data/` 各类资产的职责边界与再生方式已在开发文档固化）

### 03 · 检测回归分析

建立**跨版本检测结果对比**能力，让检测变化更加直观，帮助识别升级带来的收益与潜在问题。

- 对比不同版本的检测结果
- 识别新增发现、消失结果与状态变化
- 分析检测耗时及资源开销变化
- 辅助发现检测能力退化与兼容性问题

> **本方向已有基础**（5.1 → 5.2 期间完成）：
> - `sitelens regression <scan_id>` 子命令：重放历史扫描的已验证发现，退出码直接表达回归率
> - `tools/regression_nightly.sh` 靶场回归门禁：农场 → 矩阵 → **零误报断言** → 拆场
> - 历史库支持**双扫描 diff**（`GET /api/diff`）与漏洞检索
> - 5.2 补齐"同一漏洞跨版本分数变化"的可比对性——分数口径统一后，版本间对比才成立

### 04 · 机器学习优化

在现有机器学习检测排序能力的基础上，进一步评估模型表现，探索更可靠、更具针对性的优化方案。

- 持续评估模型预测与排序效果
- 关注误判情况及不同场景下的泛化表现
- 探索结合检测质量反馈优化模型
- 以**可验证的实验结果**指导后续迭代

> **本方向已有基础**（5.1 → 5.2 期间完成）：
> - 修复 sev-prior ONNX 通道**恒不可用**的问题（资产路径未跟随一次目录迁移，导致推理始终回退 NVD 先验）
> - 修复模型资产损坏时"整进程静默禁用"的判定缺陷（区分"缺失"与"损坏"两种降级语义）
> - 5.0 模型卡给出明确的评测口径与红线（未知/未命中/缺失**永不充当负类**）
> - 修复"模型先验会改变 check 集合"这一与产品承诺不符的语义张力（见 `bug清单-5.1.0.md` DOC-010）

## 三、用户反馈与规划的对应关系

以下为 5.2 规划期收集到的**用户侧反馈**，已逐条在代码中核实根因，并映射到上述方向。

### 3.1 已能对齐到既有方向的反馈

| 反馈 | 核实结论 | 对应方向 |
|---|---|---|
| **「failed to fetch，失败了也没有反馈信息」** | ✅ 属实。`web/js/common.js` 的 `asJson` 不区分**网络错误 / HTTP 错误 / 响应非 JSON**三种失败，`r.json()` 在网络层失败时抛出的原生 `TypeError: Failed to fetch` **不带 URL、不带原因、不带状态码**；且大量调用点用 `.catch(function(){})` **静默吞掉**异常，界面零反馈 | **01 检测质量度量**（错误可观测性是检测质量的一部分）+ 03（失败态本身需要可回归） |
| **「包体太大」** | ✅ 属实且已量化：仓库合计 **891.4MB**，其中 **ML 模型资产 748.9MB（占 84%）**，4 个 ONNX 合计 **643.3MB**（fp32 ×2 = 511MB + int8 ×2 = 132MB，**两套全量随包分发**）；另有模板包 46.8MB、情报与指纹 51.7MB | **04 机器学习优化**（模型资产瘦身与按需分发） |
| **「开启后会有强制的 cmd 窗口，关闭也是」** | ✅ 属实，两个不同根因：**启动时**——引擎 `sitelens.exe` 以控制台子系统编译（`desktop/build-engine.js:29` 的 `LDFLAGS = '-s -w'`，**缺 `-H windowsgui`**，对比壳侧 `desktop-wails/main.go:14` 是带了的），壳拉起它时必然弹黑窗，且 `main.go:114` 拉引擎时**未设 `HideWindow`**；**关闭时**——`main.go:274` 用 `exec.Command("taskkill", ...)` 树杀引擎，`taskkill` 是控制台程序 → 闪黑窗 | **04** 之外的交付体验项，见 3.2 建议新增方向 |

### 3.2 已落地的第 05 方向：交付体验与可观测性

> **诚实标注**：海报的四大方向聚焦"检测质量与数据治理"，**用户反馈里有两类问题不落在这四个方向内**——桌面端的控制台窗口扰民，以及"崩溃了不知道发生了什么、想反馈也没地方提"。为此在 5.2 规划中**新增了第 05 个方向**，把"产品可用性反馈闭环"纳入版本规划。

| 子项 | 现状（已核实） | 5.2 已做 / 待做 |
|---|---|---|
| **控制台窗口** | 启动弹窗 + 退出闪窗，两个独立根因 | ✅ **已修**：① 引擎与 CLI **拆成两个二进制**（此前一个 exe 既是引擎又是 CLI，是问题的根）；② 壳侧拉引擎/树杀/种子交付三处子进程统一加 `CREATE_NO_WINDOW` + `HideWindow` |
| **失败反馈** | 前端错误无上下文、异常被静默吞掉 | ✅ **已做**：三类失败（网络/HTTP/非 JSON）分级并带 URL 与原因；11 处静默 catch 全部改为全局错误出口；新增「引擎无响应」界面态 |
| **反馈入口** | 仅有设置页一个外部 Issues 链接 | ✅ **已做**：应用内「反馈」页，本机生成脱敏诊断包（资产就位矩阵 / 降级清单 / 最近失败记录 / 配置摘要），可预览删减后复制，或提交到**用户自建**端点 |
| **包体瘦身** | 891.4MB，其中 ONNX 643.3MB（fp32 与 int8 双份） | ✅ **阶段 1/2 已落地**：ONNX 退出默认分发，严重度改「NVD 查表 + 0.7MB `sev-linear` 线性回归兜底」（同一 600 抽样 1.189 vs 1.079，+0.11 分）；ML 资产 748.9 → 约 106 MiB，引擎载荷实测 173.8 MB（数据刷新后）；阶段 2 查表优先+指纹先验已落地。仓库 ONNX/LFS 资产与历史已清理（完整 clone 约 1.35GB → 0.5GB） |
| **埋点** | 见 3.3 | ✅ **定案**：不做常驻埋点，走「本地诊断包 + 用户主动提交」 |

### 3.3 ✅ 关于「埋点」的定案：与隐私承诺的冲突已解决

用户反馈希望"有埋点"。核实后发现，**当前产品明确承诺没有埋点**，且这句话写在《用户服务协议》里：

> `web/settings.html:454`：「本软件无账号体系、**无埋点**、无遥测、无崩溃上报、无广告组件。开发者的服务器不接收您的任何扫描数据、目标信息、机器信息、网络拓扑、使用行为或崩溃信息。开发者因此在技术上**不具备**收集或回溯您任何使用行为的能力，也无法为您监控或干预具体扫描。」

这不是遗漏，是**写进用户协议的合规卖点**。因此"加埋点"不是一个可以顺手做的修复，而是一次**产品立意变更**。

**5.2.0 的定案**：**不做常驻埋点**，改为**「本地诊断包 + 用户主动提交」**——

| 维度 | 设计 |
|---|---|
| 采集时机 | **仅在用户主动点「生成诊断包」时**，本机一次性生成 |
| 采集内容 | 资产就位矩阵 / 降级清单 / 最近失败记录 / 配置摘要（**无 token、无凭证、无 Cookie、路径只留文件名**） |
| 外发时机 | **仅在用户点「提交」时**；默认无提交地址，只能复制到 Issue |
| 提交目标 | **用户自建**（`feedback.endpoint`，内网亦可）；本项目不提供、不运营任何收集服务端 |
| 隐私影响 | 不采集任何使用行为；数据流向完全由用户决定 |

这既满足了"失败有信息、可反馈"的真实诉求，又不破坏"不采集用户数据"的承诺。

**附带收益**：诊断包的"资产就位矩阵"直接回答了"为什么某某功能没输出"——大多数"没结果"其实是某个数据资产缺失导致该能力静默降级。

> 若未来要改为常驻埋点（匿名使用统计 / 崩溃自动上报），仍需先修订《用户服务协议》与设置页的隐私声明，并决定默认开关策略。**这一项需产品侧再次拍板。**
